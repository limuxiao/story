VIEW 01 · SPRINT
01

压缩逻辑：三个月到底换了什么

12 周无法覆盖完整的全栈能力面。可行的做法不是加速，而是重新定义终点，并把有限时间全部压到同一条链路上。

换目标

从「全面」降为「端到端」

目标改为：能独立把需求从表结构做到线上，并承担全栈初级 / 中级职责。3 个月能到的是生产可用下限，不是复杂系统设计能力，这一点必须写实。

砍范围

只保留一条主链

数据建模 → 接口与鉴权 → 异步与文件 → 部署上线。第二语言栈、微服务、K8s、分布式深度、源码精读、算法刷题，全部移出本期。

提密度

一个项目贯穿 12 周

每周 15–20 小时，动手写代码占比不低于 55%。不换题、不换框架、不追前端新技术。一个能讲 30 分钟的作品，胜过三个半成品。

如果每周只有 8–10 小时：不要硬赶进度，改走第 06 节的降级方案。硬赶的典型结果是测试和文档被跳过，上线作品变成半成品，反而拿不到转型的证据。
02

目标画像与能力基线

全栈的可验证定义：一个人能把需求从数据模型走到线上，并兜住基本故障。5 分制中，3 分 = 生产可用（能自己设计、能排错、能讲清取舍）。

维度 起点 3 个月目标 达标含义
前端工程化 4 4 保持优势，本期前端只用于整合，不追新技术
后端开发 1 3 分层、DTO 校验、统一错误码、API 契约，能独立新增接口
数据建模 / SQL 1 3 能设计表、写迁移与回滚，用 EXPLAIN 定位慢查询，讲清索引理由
认证与安全 1 2.5 登录与 refresh、RBAC、资源归属校验，能过一遍 Web 安全自查
测试与质量 2 3 集成测试成为合并门槛，CI 里 lint / typecheck / test 全绿
部署运维 1 2.5 容器编排、Nginx、HTTPS、CI/CD、基础监控与备份
系统设计 1 2 能说清瓶颈与降级方案，不要求分布式实战
方案与协作 2 3 能出设计文档、参与接口评审、主导一次需求到上线的闭环

本期明确不做

  • 第二语言栈（Go / Rust / Java）
  • 微服务、K8s、服务网格
  • 分库分表、读写分离等分布式实战
  • 框架横向对比与源码精读
  • 算法刷题（除非目标外企面试）
  • 前端新框架 / 新特性追踪
三条达标判据：① 能独立把一个小需求从表结构做到线上；② 能沿「浏览器 → 网关 → 服务 → DB」定位跨端问题；③ 能讲清自己为什么不用某个方案。三者都满足，才算完成转型的第一阶段。

06

每周时间预算与降级方案

按 18 小时每周的基准分配。动手写代码是唯一不可压缩的一项。

18 小时模板

动手写主项目10h
体系化学习4h
复盘与输出2h
排错与阅读2h

体系化学习一次只跟一本书或一门课，不做教程收集者。每周最小闭环：写代码 → 提交 → CI 绿 → 一条复盘记录。

降级方案：8–10 小时每周

  • 保留 W1–W4 全部内容，以及 W9 / W10 / W12
  • W6 / W7 的队列与对象存储改为本地简化实现，只保留一条最小异步链路
  • 目标降为「端到端可上线的 CRUD + 登录 + 部署 + 文档」
  • 异步链路、缓存一致性、并发控制挪到第 4 个月续接
  • 忙周允许低配到 4 小时，但不允许整周断档
诚实提示：3 个月 + 低投入的组合，终点是「能上线、能讲清」，不是「资深全栈」。把这点写进目标，比事后发现缺口更划算。
07

作品集、履历与转型路径

作品是转型唯一的硬证据。标题和职责变更都建立在它之上。

作品与文档要求

  • 一个主项目贯穿 12 周，不换题、不重开新坑
  • README 必写：架构图、ER 图、一条命令启动、部署方式、设计取舍
  • 写清楚「为什么不用」：为什么选这个数据库、为什么没上队列、为什么单体足够
  • 攒可量化数字：表数、接口数、测试覆盖率、CI 时长、P95、可用性
  • 准备 2 个真实踩坑故事（一次数据不一致、一次线上故障）

简历改写示例

改写前

负责 XX 页面开发与接口联调。

改写后

独立交付 X 系统：设计 N 张表与迁移方案，以 OpenAPI 契约驱动前后端，实现鉴权、异步任务与进度回传，CI/CD 上线后核心链路 P95 控制在 X ms，集成测试覆盖主流程。

路径 A · 推荐优先

内部转岗

W1 就主动认领一个跨端小需求；W4 起参与接口评审与表设计；W8 争取成为某个模块 owner；W12 用上线作品和复盘申请职责调整。让「全栈」先成为事实，再成为 title。

路径 B

跳槽

W10 之后开始投，定位「能端到端交付」，不要投要求多年后端经验的岗位。重点准备 SQL / 索引 / 事务、接口设计、故障排查，以及一个能讲 30 分钟的项目叙述。

L05

投入曲线与学习方式变化

全年总投入前紧后松。Q2 起最重要的转变不是少学，而是把练习从「业余项目」搬进「真实工作需求」。

季度 每周合计 动手主项目 真实工作场景 体系学习 输出与分享
Q1 15–20h 10h 0–2h（争取认领） 4h 2h
Q2 10–12h 4h 4h 2h 1h
Q3–Q4 8–10h 2h 5h 1h 2h

为什么重心要转移

  • 业余项目干净、可控，练不到真实数据、历史包袱和跨团队协作
  • Q2 起主动认领跨端需求，把并发、兼容、评审这些难点放到真实约束里练
  • 主项目退居「试验田」：新方案先在这里验证，再带到工作中

避免割裂

最常见的失败是「业余项目很漂亮，工作里还是只写前端」。每月检查一次：这个月学到的东西，有没有在真实需求里用过至少一次？如果没有，下个月优先补这一项，而不是继续加新技术。

L07

转型路径与纵深方向

先让「全栈」成为事实，再要 title；12 个月之后选一个纵深方向扎下去，保持 T 型能力结构。

路径 A · 推荐优先

内部转岗（四步）

Q1 主动认领跨端小需求 → Q2 成为某个模块 owner → Q3 主导评审与 on-call → Q4 用作品集与复盘申请职责 / 职级变更。成本最低，且能拿到真实场景的练习场。

路径 B

跳槽（两个时间点）

Q2 末小规模试水，用来校准面试差距；Q4 正式投递，定位「能端到端交付并主导中型需求」。常考四块：SQL / 索引 / 事务、接口与系统设计、并发与故障排查、项目深挖。

纵深方向 01

服务端架构与性能

高并发、数据密集型、性能剖析与容量规划。适合喜欢啃系统底层与复杂查询的人。

纵深方向 02

平台工程与 DevOps

交付流水线、可观测性、可靠性与成本。适合对「让团队更快更稳」更有兴趣的人。

纵深方向 03

数据密集型与实时

音视频处理、实时协作、流式与队列系统。前端背景里的富交互经验在这里有复用价值。

纵深方向 04

技术负责人

需求拆解、方案取舍、评审与带人。要求补齐业务判断与沟通，而不只是技术广度。

保持 T 型：前端优势不丢（体验、工程化、类型体系仍是差异化竞争力），后端那一竖扎到能兜底线上故障。第 12 个月之后，广度不再是目标，纵深才是。

P01

实战路线定位与主线原则

这 6 个项目是「边学边做」的练习关卡，不是 6 个必须独立完成的仓库。原清单按独立作品集组织，而本规划坚持一个主项目贯穿全年，因此先明确用法再动手。

统一技术栈

NestJS + MySQL + TypeORM + Redis + Docker

配套 Nginx 反代与 GitHub Actions。与前两条计划的 Node/TS 单栈主线一致；计划正文里泛举例的 ORM，在实战中统一用 TypeORM，避免同时学两套。

核心原则

先最小可用，再迭代

每个项目先做最小版本跑通，再逐层加功能；优先自己设计表结构，不要直接抄教程的表。每个项目动手前先自己画一张 ER 图，再对照教程修正。

两种用法

推荐主线吸收式

A · 主线吸收（推荐）：选 1 个作主项目（推荐博客系统或 RBAC 后台），把另外 5 个的关键能力作为迭代模块逐个注入，全年只有一个仓库。B · 独立作品集：6 个独立仓库，覆盖面广但每个都浅，只适合每周 20 小时以上且已有后端基础。

入门级 · 刚上手 Nest / 数据库 进阶级 · 缓存、文件、权限 提高级 · 异步、事务、锁 挑战级 · 接近企业业务
与两条计划的衔接：3 个月冲刺只吸收 P1–P3 的能力点（不新建 3 个仓库），P4–P6 的能力点放到 12 个月长期计划的 Q2 / Q3 / Q4。逐项映射见 P03，避免「项目做了一堆、和计划脱节」。
