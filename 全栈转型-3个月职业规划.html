01

压缩逻辑：三个月到底换了什么

12 周无法覆盖完整的全栈能力面。可行的做法不是加速，而是重新定义终点，并把有限时间全部压到同一条链路上。

换目标

从「全面」降为「端到端」

目标改为：能独立把需求从表结构做到线上，并承担全栈初级 / 中级职责。3 个月能到的是生产可用下限，不是复杂系统设计能力，这一点必须写实。

砍范围

只保留一条主链

数据建模 → 接口与鉴权 → 异步与文件 → 部署上线。第二语言栈、微服务、K8s、分布式深度、源码精读、算法刷题，全部移出本期。

提密度

一个项目贯穿 12 周

每周 15–20 小时，动手写代码占比不低于 55%。不换题、不换框架、不追前端新技术。一个能讲 30 分钟的作品，胜过三个半成品。

如果每周只有 8–10 小时：不要硬赶进度，改走第 08 节的降级方案（具体时段排法见第 06 节）。硬赶的典型结果是测试和文档被跳过，上线作品变成半成品，反而拿不到转型的证据。

NestJS + MySQL + TypeORM + Redis + Docker

核心原则

P1全栈 Todo 任务管理系统

入门级

学习目标

  • 掌握 Nest 基础分层：Controller / Service
  • TypeORM 基础、MySQL 单表设计
  • JWT 登录鉴权、基础参数校验、统一异常返回

技术栈

Vite（React/Vue）+ NestJS + MySQL + TypeORM

最小版本 · 必做

注册、登录、创建 / 编辑 / 删除任务、任务状态切换、分页列表

迭代扩展

任务分类、标签、截止时间、简单筛选；用 Docker Compose 拉起整套环境

验收标准

不同用户只能看到自己的任务；接口有统一返回体；能在本地容器一键启动

P2个人博客系统

进阶级

学习目标

  • 多表关联设计（用户、文章、分类、评论）
  • Redis 缓存热点数据（首页文章列表）
  • 文件上传、图片存储、CORS、RBAC 简单权限

技术栈

前端自选 + NestJS + MySQL + Redis + Nginx

最小版本 · 必做

文章发布 / 编辑 / 删除、分类、评论、游客浏览、作者登录管理后台

迭代扩展

Markdown 渲染、阅读统计、点赞、文章搜索、Redis 缓存首页、Nginx 反向代理部署上线

验收标准

会写联表 SQL、会用 EXPLAIN 看慢查询；缓存失效逻辑正常；图片上传有类型与大小校验，防止恶意文件

P3在线文件网盘（简易版）

进阶级

学习目标

  • 大文件上传、分片上传、断点续传
  • 文件权限、分享链接、过期控制
  • 理解静态资源服务、安全校验（文件后缀、MIME）

技术栈

前端 + NestJS + MySQL + Redis

最小版本 · 必做

文件夹管理、单文件上传下载、删除、预览图片

迭代扩展

分片上传、分享链接 + 提取码 + 过期时间、限流、对象存储（OSS）对接

验收标准

不能上传脚本文件；分享链接过期自动失效；分片中断后可以续传

P4简易商城（商品 + 订单）

提高级

学习目标

  • 数据库事务、库存扣减、并发问题
  • Redis 分布式锁，防止超卖
  • 异步任务（消息队列）、支付回调处理

技术栈

前端 + NestJS + MySQL + Redis + MQ（可选）

最小版本 · 必做

商品管理、购物车、下单、库存扣减、订单列表、订单状态

迭代扩展

优惠券、秒杀、分布式锁防超卖、模拟支付回调、订单超时自动取消（延时任务）

验收标准

高并发下单不会出现超卖；下单失败事务回滚；订单超时自动关闭

P5实时聊天室（IM）

提高级

学习目标

  • WebSocket 服务端实现、心跳保活、断线重连
  • 在线状态管理、消息持久化
  • Redis Pub/Sub 做多实例消息广播（横向扩展思路）

技术栈

前端 + NestJS Gateway + MySQL + Redis

最小版本 · 必做

私聊、消息发送、历史消息查询、在线状态展示

迭代扩展

群聊、消息已读、消息撤回、图片消息、Redis Pub/Sub 跨服务转发消息

验收标准

断网重连后不丢消息；心跳超时自动标记离线；消息落库持久化

P6运营后台管理平台（通用权限系统）

挑战级

学习目标

  • 完整 RBAC 权限模型：用户 - 角色 - 菜单 - 按钮权限
  • 接口级权限控制、数据权限控制
  • 日志审计、操作记录、CI/CD 自动部署

技术栈

React/Vue Admin + NestJS + MySQL + Redis + GitHub Actions

最小版本 · 必做

用户管理、角色管理、菜单配置、页面权限控制

迭代扩展

数据权限（只能看本部门数据）、操作日志、登录验证码、账号锁定、自动部署流水线

验收标准

不同角色看到不同菜单；接口层面二次校验权限，不能只靠前端隐藏按钮

原清单推荐顺序

  1. Todo 系统：熟悉 Nest、JWT、基础 CRUD、数据库单表
  2. 博客系统：多表关联、Redis 缓存、文件上传、Nginx 部署
  3. 简易网盘：分片上传、文件安全、分享过期机制
  4. 聊天室：WebSocket 实时通信、心跳、Redis 发布订阅
  5. 简易商城：事务、锁、并发、异步任务，难点集中在这里
  6. RBAC 后台：企业级权限、审计日志、CI/CD，放进简历

本规划采用顺序

  1. Todo → Q1 骨架
  2. 博客 → Q1 内容与上线
  3. 网盘 → Q1 文件模块
  4. 商城 → Q2 事务、并发与压测
  5. 聊天室 → Q3 可靠性与实时
  6. RBAC 后台 → Q4 主导与作品集

按能力曲线排，而不是单按难度排：Q2 的主题正是数据一致性与并发，商城刚好承接；Q3 的主题是可靠性与实时，聊天室承接。

顺序差异说明：原清单编号 4 是商城、5 是聊天室，但推荐实践顺序里聊天室排在商城之前（先易后难、把并发难点后置）。本规划按能力曲线把商城提前到 Q2、聊天室放到 Q3。两种顺序都不改变 G1–G6 的验收内容，可按个人节奏选择，推荐后者以贴合季度主题。
