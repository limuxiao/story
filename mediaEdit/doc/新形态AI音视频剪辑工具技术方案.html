1. 项目背景

1.1 行业趋势

  • 内容生产平民化：短视频、直播、数字人、在线课程等内容形态爆发，剪辑需求从专业团队下沉到海量普通创作者。
  • Web / 移动端剪辑被验证：剪映、CapCut 证明了"轻量、模板化、低门槛"剪辑工具的巨大市场，且网页版正在成为重要入口。
  • 专业合成的标杆：Adobe After Effects（AE）代表了图层合成 / 关键帧动画 / 特效的天花板，但其门槛与重量级使其难以普及。
  • 大模型重新定义"剪辑"：多模态大模型（语音识别、视频理解、文生视频、对话式交互）正在把剪辑从"手动操作"推向"自然语言驱动 / 智能自动化"。

1.2 现有方案的核心痛点

  • 桌面软件（Premiere / AE）：安装重、跨平台差、协作与云化困难，对普通用户门槛高。
  • 纯 Web 剪辑器的内存死结：浏览器默认会把大文件整体加载进内存（尤其 FileReader.readAsArrayBuffer 或 ffmpeg.wasm 全量解码），一个 1GB 视频上轨即 +1GB 内存，几个片段就撑爆。
  • 闭源 SaaS（剪映网页版、VEED、Kapwing）：数据不自主、定制能力受限、能力边界由厂商决定。
  • 开源方案的两极：要么是"程序化生成"型（如 Remotion，用代码声明视频，适合模板而非自由剪辑），要么是"玩具 demo"型（处理能力仅限几十 MB），缺乏"自由剪辑 + 专业合成 + AI"三位一体的可二次开发基座。

1.3 我们要解决的问题与目标

核心诉求：在浏览器内高效剪辑大体积音视频资源，绝不因素材体积导致内存爆炸；支持多轨时间轴、转场、特效与多视频同屏合成；并原生集成 AI 大模型能力，体验对标剪映的交互易用性与 AE 的合成表现力。

关键认知："上轨"不等于"加载文件"。轨道只保存一份元数据描述（JSON），引用后端生成的代理 MP4（前端 mp4box 解封装 + WebCodecs 窗口化解码）；网络层仅拉取体积小巧的代理文件，解码层只保留播放头附近帧、旧帧即 close() 释放，故内存恒定。原片仅在服务端导出时露面。这正是解决内存压力的根本路径。

2. 产品定位

一句话定位

一款 AI 优先、浏览器内运行的轻量音视频剪辑 / 合成工具，让普通人也能完成"接近 AE 表现力"的成片。

目标用户

短视频创作者、运营、教育者、数字人 / 直播从业者，以及需要"快速出片 + 一定专业度"的中小团队。

差异化

AI 原生驱动 + 模式 B 图层合成 + 数据可自主 / 可自托管，区别于普通 Web 剪辑器与闭源 SaaS。

非目标

不追求"全功能替代 Premiere + AE"，而是做"足够好用 + AI 增强"的轻量专业工具。

战略判断：把期望从"做一个剪映 + AE"调整为"做一个 AI 驱动的、足够好用的轻量剪辑 / 合成工具"。后者真实可行且有竞争力；前者工程量与生态鸿沟不可及。AI 能力跑在后端推理，天然不压前端算力，是我们的结构性优势。

3. 功能介绍

3.1 剪辑核心

  • 多轨时间轴：视频轨、音频轨、图片轨、文字轨、特效轨，支持轨道增删、锁定、隐藏、层级排序。
  • Clip 操作：裁剪、分割、吸附对齐、变速（含曲线）、音量、位移 / 缩放 / 旋转、透明度。
  • 关键帧动画：对任意可视属性（位置 / 缩放 / 透明度 / 滤镜参数）打关键帧，支持线性 / 贝塞尔插值。
  • 工程结构：以 JSON 描述序列（分辨率、帧率）、轨道、Clip（入出点、源引用、特效列表）、转场、关键帧。

3.2 合成与特效（模式 B）

采用 模式 B（全帧合成）：每一帧把各视频源画面上传为 WebGL 纹理，在 shader 中按轨道层级与转场函数混合，再叠加特效，最后输出。支持多视频同屏合成。

特效类别前端实现方式典型示例
调色 / 滤镜 / LUTfragment shader 逐像素运算；LUT 用 3D 纹理 / 2D LUT 图采样亮度 / 对比度 / 风格化滤镜
变换 / 3D 翻转 / 透视vertex shader 变换顶点坐标 + 变换矩阵旋转、缩放、翻页
转场混合两纹理，系数由转场进度 t 驱动溶解、滑动、翻页、遮罩擦除
抠像 / 蒙版色键（按颜色距离剔除）/ mask 纹理 alpha 调制绿幕抠像、局部蒙版
模糊 / 辉光 Bloom多 pass：降采样 → 模糊 → 叠加背景虚化、发光
扭曲 / 水波噪声纹理做 UV 位移（displacement map）水波、液化
粒子 / 光效GPU 粒子系统（GPGPU）或预渲染 sprite 序列帧烟花、光斑
文字 / 字幕canvas 2D 渲染成纹理再合成，动画走 transform标题、动态字幕

溶解转场 shader 示例（直观说明前端如何落地）：

uniform sampler2D fromTex;
uniform sampler2D toTex;
uniform float progress;     // 0..1，由转场区间时间插值得到
uniform sampler2D noiseTex; // 噪声图决定溶解蔓延顺序
varying vec2 vUv;
void main() {
  float n = texture2D(noiseTex, vUv).r;
  float m = step(n, progress);
  vec4 a = texture2D(fromTex, vUv);
  vec4 b = texture2D(toTex, vUv);
  gl_FragColor = mix(a, b, m);
}

3.3 预览与导出

  • 实时预览：基于主时钟驱动渲染管线，配合性能降级策略保证流畅（详见第 7 章）。
  • 服务端导出（前端仅预览）：前端只负责实时预览（低保真 WebGL 合成），不参与导出；导出完全在服务端由 ffmpeg 按原片分辨率 + 工程 JSON 重新合成。预览与导出是两条独立渲染路径（一致性见第 9 章）。

3.4 AI 能力矩阵

自动字幕 / 转录

语音识别生成时间轴字幕，支持多语种、校对。

智能粗剪

视频理解自动挑选精彩镜头、去除静默段，生成粗剪时间轴。

智能抠像

分割模型去背景，替代传统绿幕色键。

文生特效 / 转场

LLM 生成特效参数（或受限 shader），自然语言描述即出效果；生成代码须经校验 / 沙箱后再编译，避免注入与运行时错误。

对话式编辑

"把这段加速并加淡入"→ 解析为工程 JSON 操作。

智能配音 TTS

多音色配音，自动匹配语速与情绪。

4. 技术方案选型

4.1 选型原则

没有单一"全家桶"开源项目能覆盖全部能力（前端编辑器 UI + 轨道 + WebGL 合成引擎 + 后端分片转码 + 服务端导出）。因此采用分层选型、拼装成基座的策略，每层挑选最成熟 / 最契合的组件。

4.2 分层推荐表

层推荐基座理由二次开发改造点
前端轨道 UI自研（参考 OpenCut 交互）无成熟"视频时间轴组件"可复用，必须深度定制模式 BOpenCut 仅作交互与工程结构参考，谨慎直接 fork
WebGL 合成引擎（核心）PixiJS v8场景图 / 图层栈 + Filter 滤镜系统（自定义 shader）+ 渲染循环，最贴合模式 B接主时钟渲染循环、把 WebCodecs 帧做成纹理、写自定义特效 Filter
解封装 / 解码mp4box + WebCodecsmp4box 解封装单文件 MP4，VideoDecoder / AudioDecoder 在 Worker 精确解码为 VideoFrame / AudioData，经 transfer 回主线程后上传纹理 / 送入 Web Audio；全程无 <video> / <audio> 元素纯 WebCodecs 路线，彻底摒弃 <video> 元素（见 5.2）；解码放 Worker 且窗口化，只解码播放头附近帧
后端分片转码ffmpeg（fluent-ffmpeg）或 Cloudflare Stream / Muxffmpeg 转代理 MP4 是事实标准；云服务"上传即转码"省去自建转码（输出同样为单文件 MP4 供前端 mp4box 解封装）自托管需搭转码服务 + 对象存储；借云则只调 API 拿 URL
服务端导出ffmpeg（服务端）前端仅预览、不参与导出；ffmpeg filter 链在服务端按工程 JSON 复现剪辑 / 转场 / 滤镜，输出原片分辨率成片前端 shader 特效需有对应服务端实现（或自建 WebGL offscreen 渲染）；预览与导出一致性是后续专题（见 9.1）
工程数据结构参考 Editly JSON schemaclips / layers / transitions 结构清晰，可直接借鉴按特效 / 关键帧模型扩展
AI 推理大模型 API（ASR / LLM / 分割 / TTS）能力跑后端，前端只触发与展示结果回写为工程 JSON 节点

4.3 关键说明

OpenCut 适合"抄"不适合"fork 当基座"：它是 2025 年新兴开源项目（目标为开源版 CapCut），交互与工程结构值得逐行研究，但项目年轻、与自身后端耦合，直接二次开发风险高。
前端只预览，导出全在服务端：预览走前端 WebGL 低保真合成（为实时性优化），导出由服务端 ffmpeg 按工程 JSON 重新合成（原片分辨率、精确）。两者渲染路径不同，特效 / 转场在预览与导出间的一致性、以及对大量常用特效转场的支持，是后续需专题讨论的议题（见 9.1），本方案不假设"预览即导出"。

4.4 推荐组合

组合构成适用
A 借云服务（可选，非默认）自研 UI + PixiJS + 云服务转码(Cloudflare Stream / Mux) + 前端 WebCodecs(mp4box) 解码 + 服务端 ffmpeg 导出不碰转码后端、快速起步；但媒体走第三方云，数据自主优势不成立，故不作为默认
B 全自托管（默认）自研 UI + PixiJS + 后端 ffmpeg 切 MP4(代理) + 前端 WebCodecs(mp4box) 解码 + 后端 ffmpeg 导出数据 / 算力自主，契合核心差异化；工作量较 A 翻倍
首选建议：直接采用组合 B（全自托管），把数据自主作为优先。组合 A 云服务仅作为可选兜底（媒体会经第三方云，数据自主优势不成立）。合成引擎锁定 PixiJS；人力集中在最稀缺、最该自掌握的轨道 UI 与 WebGL 合成引擎。

5. 核心架构

5.1 整体架构

浏览器前端

轨道 UI · PixiJS 合成引擎 · mp4box + WebCodecs(Worker) · 性能降级层

↑ 工程 JSON / 指令　↓ 代理 MP4(mp4box 解封装) / 渲染结果

API 网关

鉴权 · 工程存取 · 任务调度

分片转码服务

ffmpeg / Mux：上传即转代理 MP4 + 低码率代理

AI 推理服务

ASR / LLM / 分割 / TTS：结果回写工程 JSON

导出合成服务

ffmpeg / GPU：按原片 + JSON 精确合成

↕ 对象存储（可自托管，如 MinIO 等 S3 兼容）+ CDN（可选）

5.2 前端架构

  • 轨道 UI 层：时间轴、Clip、playhead、拖拽交互；只读写工程 JSON，不直接持有媒体。
  • 合成引擎层（PixiJS）：图层栈（Container）+ 自定义 Filter（shader）构成多 pass 管线；每个 Clip 对应输入纹理源。
  • 播放 / 解码层：mp4box 解封装单文件 MP4，WebCodecs 在 Worker 精确解码为 VideoFrame / AudioData，经 transfer 回主线程后上传纹理 / 送入 Web Audio；全程无 <video> / <audio> 元素，且按播放头窗口化解码（只解码当前窗口 + 预解码未来 1–2 秒）。
  • 主时钟与同步：单一播放头时间驱动所有轨道；每帧在各源上按播放头取对应 VideoFrame（窗口化解码、旧帧释放），超出解码窗口则触发重新解码校正。
  • 性能降级层：按设备能力调节分辨率 / 帧率 / 同屏解码路数（详见第 7 章）。

5.3 后端架构

  • 分片转码服务：上传后异步转码出低码率代理 MP4（供前端 mp4box 解封装 + WebCodecs 窗口化解码）；原片独立保存，仅导出时引用。
  • AI 推理服务：异步任务队列，推理结果（字幕、粗剪、抠像蒙版、特效参数）回写为工程 JSON 节点。
  • 导出合成服务：读取工程 JSON + 原片，ffmpeg 复现剪辑 / 转场 / 滤镜，输出成片。
  • 对象存储（自托管优先）：分片 / 代理 / 原片 / 成片存于可自托管的对象存储（如 MinIO 等 S3 兼容），数据自主可控；CDN 为可选加速层。

5.4 数据流

工程 JSON（核心资产）

{
  "sequence": { "width": 1920, "height": 1080, "fps": 30 },
  "tracks": [
    { "type": "video", "clips": [
      { "sourceId": "vid_01",
        "srcIn": 2.0, "srcOut": 8.0,
        "timelineStart": 0.0,
        "effects": [ { "type": "lut", "params": { "intensity": 0.8 } } ],
        "transitions": [ { "type": "dissolve", "duration": 1.0 } ] }
    ]},
    { "type": "audio", "clips": [ /* ... */ ] }
  ]
}
// Source 引用后端代理 MP4（前端 WebCodecs 解封装，URL 由自托管对象存储签发），原片仅在导出时引用
{ "id": "vid_01", "previewUrl": "/mp4/vid_01/clip.mp4", "originalUrl": "/origin/vid_01.mp4" }

每帧渲染管线

  1. 主时钟推进到时间 t
  2. 计算各 Clip 在 t 的可见性、入出点、转场进度
  3. 对各可见视频源：用 WebCodecs 取到对应时间的 VideoFrame，copyExternalImageToTexture / texImage2D 上传纹理
  4. 跑 shader 多 pass（图层底→顶 blend + 各特效 Filter）
  5. 最终帧输出屏幕 canvas

5.5 内存 / 性能架构

  • 窗口化解码：代理 MP4 体积小，且前端仅解码播放头附近帧、旧帧即 close() 释放，内存恒定（非整段全量解码）。
  • 代理：预览用低码率 / 低分辨率，原片从不进浏览器。
  • 显存管理：纹理池 / FBO 复用，及时 close() / delete()；超限即降分辨率。
  • 图片不分片：直接加载；超大图（> 纹理上限）降级分辨率或分块。

6. AI 集成设计

6.1 接入范式

所有 AI 能力遵循统一范式：前端触发 → 后端异步推理 → 结果回写为工程 JSON 节点。AI 不占用前端算力，不破坏实时预览体验。

6.2 能力清单与对接

能力输入后端处理回写产物
自动字幕音频 / 视频ASR 转录字幕 Clip（带时间轴）
智能粗剪视频内容理解 / 镜头打分裁剪后的 Clip 序列
智能抠像视频 / 图片分割模型蒙版 / 扣像特效节点
文生特效自然语言LLM → 受限参数 / shader（经校验沙箱）自定义特效 Filter 配置
对话式编辑自然语言指令LLM → 操作序列工程 JSON 变更
智能配音文本TTS音频 Clip

6.3 不破坏实时预览的设计

  • 异步 + 占位：AI 任务提交后，时间轴先显示占位 Clip，结果就绪后无缝替换。
  • 结果即数据：AI 产出是工程 JSON 节点，预览管线无需 special case，与手动编辑产物一致。
  • 可撤销：所有 AI 修改进入同一套 undo / redo 栈。

7. 性能与降级策略

重要认知：模式 B 预览必然存在卡顿风险（多路解码 + 多 pass 填充率 + 纹理带宽 + 显存）。专业软件（PR / AE）也靠降级策略化解，预览只为"判断效果对不对"，不为交付；导出走服务端。

7.1 卡顿来源

源头原因严重度
多路解码同屏 N 路 1080p 实时解码抢算力（WebCodecs 多路亦然，故需窗口化 + Worker）最大
填充率多 pass 全屏像素累加，1080p × 10 pass 每帧约 2 亿像素运算高
纹理上传带宽多路视频每帧 texImage2D 上传 GPU高
显存多纹理 + 多 FBO + 特效中间结果高
特效本身重模糊 / Bloom / 粒子多趟中
JS 主线程 + 同步抖动图层遍历 / 插值阻塞 rAF；解码跟不上播放中

7.2 性能三旋钮

预览性能 = f(分辨率, 帧率, 同屏路数)
            480p/720p   15-30fps   2-4 路
// 设备越弱，三旋钮向左拧；导出全拧到最大（原分辨率/源帧率/全路数），但导出走服务端

7.3 分级策略清单

  • 代理分辨率：预览跑 480p / 720p，导出原分辨率（最有效）。
  • 动态帧率 / 跳帧：scrub 时降到 15–24fps；实时跟不上丢中间帧保流畅。
  • 限制同屏解码路数：仅保留时间窗内可见源解码，出窗释放；用 WebCodecs 精确取帧。
  • 特效分级（LOD）：预览用廉价近似，导出用精确版。
  • 选择性渲染：静态图层缓存位图不每帧重合成；仅变化区域重跑 shader。
  • 显存预算 + 资源复用：纹理池 / FBO 复用，监控超限降分辨率。
  • 解码放 Worker：WebCodecs 在 worker 解，不阻塞主线程；预解码未来 1–2 秒帧。

8. 项目优势

内存安全

代理 + 窗口化解码 + 降级，大文件上轨不再 +1GB 内存，几个片段也不撑爆。

AI 原生

AI 跑后端推理，前端仅触发 / 展示，不压算力，结构性区别于传统编辑器。

数据自主

可自托管（组合 B），工程 / 素材 / 成片全可控，不受 SaaS 边界限制。

模式 B 护城河

多数 Web 剪辑器仅模式 A；多视频同屏合成 + 自定义 shader 特效形成区隔。

数据自主优先

默认全自托管（组合 B），数据 / 算力完全自主；云服务仅作可选兜底，技术债务可控。

跨平台

纯浏览器入口，天然跨端，协作与云化成本低。

9.1 主要风险与缓解

  • 工程量巨大 → 聚焦差异化（AI + 模式 B），不做全功能对标。
  • 特效资产生态不足 → 优先内置高频特效 + AI 生成特效，降低对素材库的依赖。
  • 复杂工程性能 → 持续调优降级策略，导出走服务端兜底。
  • AI 推理成本 / 时延 → 异步任务 + 占位，不阻塞编辑流；热点能力缓存。
  • 浏览器能力边界 → WebGL 精度 / 编解码 / 移动端性能设下限，必要时引导客户端。
  • 预览 ≠ 导出（一致性待专题） → 前端预览走 WebGL 低保真合成，导出走服务端 ffmpeg，两条渲染路径不同；特效 / 转场在两端的一致性、以及对大量常用特效转场的支持，是后续需专题讨论的议题，本方案不假设"预览即导出"。

10. MVP / Demo 规划

目标：构建一个中小型体量 demo，验证核心功能与交互是否成立，而非一次性做全。采用组合 B（全自托管）（PixiJS + 后端 ffmpeg 转代理 + 前端 WebCodecs(mp4box) 解码 + 服务端 ffmpeg 导出），以数据自主为先。
