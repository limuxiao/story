01

Git 仓库与分支基线

读完你要能做到：让「哪些提交可以上线」这件事由仓库规则保证，而不是靠人不推错分支。

  • 单仓组织：单人项目推荐把 src/（前后端）、Jenkinsfile、Dockerfile、deploy/（K8s 清单）放同一个仓库。好处是一次 commit 就锁定「代码 + 构建方式 + 部署形态」，回滚时能精确复现。
  • 分支模型用简化 trunk-based：main 常驻且随时可发布，feat/* 短生命周期，PR 合入后删除；发布用 release/* 或 tag。不要养长期存在的 develop 分支，它会让「哪个分支对应线上」变模糊。
  • 保护分支是自动发布的前提：main 开启 Require a pull request、Require status checks to pass（把 W8 的 ci/lint + ci/test 挂上）、禁止 force push 与删除。只有规则可信，「push 到 main 就发布」才安全。
  • 凭证最小权限：Jenkins 拉代码用 Deploy Key（SSH 公钥，只读、按仓库粒度）或 fine-grained PAT；推送镜像用另一个只写 packages 的 PAT。绝不使用个人账号密码，也不要给 Deploy Key 写权限。
  • push 事件必读字段：header X-GitHub-Event: push、X-GitHub-Delivery（每次投递唯一 ID）、X-Hub-Signature-256（HMAC-SHA256）；body 里 ref（如 refs/heads/main）、after（目标 commit SHA）、deleted、created。tag push 的 ref 是 refs/tags/v1.0.0，格式不同。
  • 签名必须基于原始 body：GitHub 对原始字节算 HMAC，接收端要先拿到 raw body 再 JSON.parse；一旦 parse 后重新 stringify，键顺序 / 空格变化会让签名对不上。比较用 timingSafeEqual，不要用 ===。
  • 投递语义：至少一次、可能重复、不保证顺序；GitHub 等待响应约 10 秒，超时即失败，可在仓库 Webhooks → Recent Deliveries 里 Redeliver。因此接收端必须「立刻返回 2xx + 异步处理 + 按 delivery ID 幂等」。

HMAC 校验 + 分支过滤（TypeScript，可直接放进 W4 的 NestJS 项目）import { createHmac, timingSafeEqual } from 'node:crypto';

export function verifyGithubSignature(raw: Buffer, sig256: string | undefined, secret: string): boolean {
  if (!sig256) return false;
  const mine = Buffer.from('sha256=' + createHmac('sha256', secret).update(raw).digest('hex'));
  const theirs = Buffer.from(sig256);
  return mine.length === theirs.length && timingSafeEqual(mine, theirs);
}

export function deployBranch(ref: string | undefined, deleted: boolean): string | null {
  if (deleted || !ref) return null;                       // 删分支不是发布
  const branch = ref.startsWith('refs/heads/') ? ref.slice(11) : null;
  return branch && ['main', 'release'].includes(branch) ? branch : null;
}
常见坑：用个人 PAT 且开了 repo 全权限；把 .env / kubeconfig 提交进仓库；分支判断只写 ref.endsWith('main')（refs/heads/not-main 也会命中）；忽略 deleted 导致删除分支触发一次部署；签名校验用了 parse 后的对象；把 HMAC secret 写死在 Jenkinsfile 里。
自测
  1. 为什么保护分支要挂在自动发布之前？→ Webhook 把「push main」等同于「上线」，若 main 可直推且无 CI 校验，等于把发布权限开放给任意一次误提交。
  2. 收到两次内容相同的 push 投递，应该以什么为准？→ 以 X-GitHub-Delivery 幂等去重，并以 payload 的 after SHA 作为部署目标，不要用「当前 HEAD」（投递可能乱序）。

Jenkins 打包服务搭建与 Pipeline

读完你要能做到：用一条命令起一个 Jenkins，写一份随仓库版本化的 Jenkinsfile，产出带 commit SHA 的镜像。

  • 官方镜像 + 命名卷：jenkins/jenkins:lts-jdk17。全部状态在 /var/jenkins_home（job、构建历史、插件、Credentials），必须挂命名卷，否则容器一删全丢——这与 W10 里 MySQL 的 volume 是同一个道理。50000 端口给 inbound agent，本期不用可不映射。
  • 初始化：initialAdminPassword 解锁 → 安装推荐插件 → 再补 Git、Pipeline、Credentials Binding、Generic Webhook Trigger、Docker Pipeline。Jenkins 首次启动约 1–2 分钟。
  • Pipeline as Code：构建逻辑写进仓库根的 Jenkinsfile（Declarative 语法），job 只负责「指向哪个仓库」。这样流水线变更也走 PR 评审，不会有人偷偷改 UI 配置。Scripted Pipeline 本期不碰。
  • Credentials 四类要对号入座：Secret text（webhook token / HMAC secret）、Username with password（GHCR 登录）、Secret file（kubeconfig）、SSH Username with private key（Deploy Key）。用 withCredentials([...]) 绑定成环境变量，Jenkins 会自动在日志里打码；不要 echo 出来自查。
  • 镜像 tag 用不可变 SHA：沿用 W11 的结论，tag = git rev-parse --short=8 HEAD。latest 可以额外打用于人工查看，但绝不能作为部署依据（K8s 对 latest 隐式 imagePullPolicy: Always，节点缓存还会让各副本版本不一致）。
  • 把 docker.sock 挂进 Jenkins 是重大风险：等价于把宿主机 root 交给流水线里任何一份 Jenkinsfile。单人学习可接受但要知道代价；正式环境应改用独立 agent、Kaniko / BuildKit 远程构建，或把构建交给外部 CI。
  • 不要在 controller 上跑构建：官方建议 controller 只做调度。本期单机用 agent any 图省事，写进 ADR 的「后果」里，触发多人协作时补 agent 节点。
  • 稳定性三件套：disableConcurrentBuilds() 防止两个 push 并发部署互相覆盖、buildDiscarder 控制磁盘、post { always { cleanWs() } } 清理工作区避免 node_modules 跨构建污染。
  • when { branch 'main' } 有生效前提：它依赖 BRANCH_NAME 环境变量，只在 Multibranch Pipeline 里存在；普通 Pipeline 拿到的是 env.GIT_BRANCH，且常带 origin/ 前缀。选错 job 类型会导致「main 也不部署」或「所有分支都部署」。

Jenkinsfile（Declarative Pipeline，放仓库根目录）pipeline {
  agent any
  options {
    disableConcurrentBuilds()
    buildDiscarder(logRotator(numToKeepStr: '20'))
    timestamps()
  }
  stages {
    stage('Checkout') {
      steps {
        checkout scm
        script {
          env.IMAGE_TAG = sh(returnStdout: true,
            script: 'git rev-parse --short=8 HEAD').trim()
        }
      }
    }
    stage('Verify') {
      steps {
        sh 'corepack enable && pnpm i --frozen-lockfile && pnpm lint && pnpm typecheck && pnpm test'
      }
    }
    stage('Build image') {
      steps { sh 'docker build -t ghcr.io/you/story-api:$IMAGE_TAG .' }
    }
    stage('Push image') {
      steps {
        withCredentials([usernamePassword(credentialsId: 'ghcr',
            usernameVariable: 'REG_USER', passwordVariable: 'REG_TOKEN')]) {
          sh 'echo "$REG_TOKEN" | docker login ghcr.io -u "$REG_USER" --password-stdin'
          sh 'docker push ghcr.io/you/story-api:$IMAGE_TAG'
        }
      }
    }
    stage('Deploy') {
      when { branch 'main' }              // 仅 Multibranch Pipeline 有 BRANCH_NAME
      steps {
        withCredentials([file(credentialsId: 'kubeconfig', variable: 'KUBECONFIG')]) {
          sh 'kubectl -n story set image deployment/api api=ghcr.io/you/story-api:$IMAGE_TAG'
          sh 'kubectl -n story annotate deployment/api kubernetes.io/change-cause="build $BUILD_NUMBER $IMAGE_TAG" --overwrite'
          sh 'kubectl -n story rollout status deployment/api --timeout=180s'
        }
      }
    }
  }
  post {
    always  { cleanWs() }
    failure { echo '流水线失败：镜像未发布或集群未变更，请查 Console Output' }
  }
}
与 W11 对照：这里的 Verify → Build → Push → Deploy 和 GitHub Actions 的 job 顺序一一对应，差别只在「谁提供 runner、凭证放哪、如何被触发」。学会一套，另一套只是换个配置文件。kubectl --record 已弃用，改用 change-cause annotation 才能在 rollout history 里看到每次发布对应哪个构建。
常见坑：忘了挂 jenkins_home 导致重启后 job 全没；把 PAT / kubeconfig 写进 Jenkinsfile；部署用 latest；构建失败却仍执行了 deploy（没把部署放在测试之后的 stage）；并发构建互相覆盖镜像 tag；rollout status 没设超时，流水线永久挂住；挂载 docker.sock 却把 Jenkins 暴露到公网。
自测
  1. 为什么镜像 tag 用 commit SHA 而不是 latest？→ SHA 不可变且可追溯到具体提交，回滚就是重新指向旧 tag；latest 会被覆盖、隐式触发 Always 拉取、各节点缓存可能不一致。
  2. 某次 push 到 main 后 Deploy 阶段被跳过，最可能的原因？→ job 不是 Multibranch Pipeline，BRANCH_NAME 不存在，when { branch } 判定为 false；改用 Multibranch 或按 env.GIT_BRANCH 判断（注意 origin/ 前缀）。

Webhook 监听特定分支提交并发布

读完你要能做到：push main 自动出镜像并更新集群，push feat/* 完全不触发部署，且伪造 / 重放的投递不会造成事故。

  • 三条路线，先选最简单的：
    A. GitHub Webhook → Multibranch Pipeline 的分支扫描（官方内置，按 Jenkinsfile 自动发现分支，when { branch 'main' } 天然生效）；
    B. GitHub Webhook → 自建中继（签名校验 + 分支过滤 + 幂等）→ Generic Webhook Trigger 插件 → 普通 Pipeline（更灵活，GitLab / Gitea 也适用，本周以 B 为主练手）；
    C. Jenkins 轮询 SCM——延迟高、空转消耗，不要用。
  • GitHub 侧配置：Settings → Webhooks → Add webhook。Payload URL 填中继地址（如 https://hooks.example.com/hooks/github），Content type 选 application/json，Secret 填一个高熵随机串并同时存到 Jenkins hook-secret，事件选 Just the push event。本地无公网 IP 时用 Cloudflare Tunnel / ngrok 做临时穿透，或让 GitHub 走可访问的反向代理。
  • 分支过滤要做三层：GitHub 端只订 push 事件；中继端白名单 main / release；Jenkins 端再用 regexpFilterExpression 和 when { branch } 兜底。只做一层的话，「新建 release 分支」「删除分支」「tag push」都可能误触发一次部署。
  • 幂等靠 X-GitHub-Delivery：用 W5 的 SET key 1 NX EX 600 抢锁，抢不到直接返回 duplicate。GitHub 会重投、用户会点 Redeliver、网络会重试，没有这层就会重复部署甚至重复执行迁移。
  • 响应要快，工作要异步：GitHub 约 10 秒超时。中继只做校验 + 去重 + 调一次 Jenkins 触发接口（该接口本身是排队后立刻返回），然后 200；绝不在中继里等构建或等 rollout status。
  • 安全边界：HMAC secret 只存在环境变量 / Jenkins Credentials；Jenkins 触发端点另设独立 token，禁止匿名 Job.Build 权限；反代可加 GitHub 来源 IP 白名单；投递处理失败要记 deliveryId / branch / sha / buildId，便于对照 Recent Deliveries 排查。
  • 顺序不保证：两次连续 push 的投递可能倒序到达，部署目标必须取 payload 里的 after SHA，不能取仓库当前 HEAD，否则可能把旧版本当新版本发上去。更稳的做法是在 Deploy 阶段校验「目标 SHA 不早于当前线上 SHA」。
github-webhook.controller.ts（NestJS 中继，复用 W4 / W5 的 Redis）// main.ts：必须开启原始 body，否则签名永远校验不过
// const app = await NestFactory.create(AppModule, { rawBody: true });

import { createHmac, timingSafeEqual } from 'node:crypto';
import { Controller, Post, Req, Headers, ForbiddenException, HttpCode } from '@nestjs/common';
import { RawBodyRequest } from '@nestjs/core';
import type { Request } from 'express';

function valid(raw: Buffer, sig: string | undefined, secret: string): boolean {
  if (!sig) return false;
  const mine = Buffer.from('sha256=' + createHmac('sha256', secret).update(raw).digest('hex'));
  const theirs = Buffer.from(sig);
  return mine.length === theirs.length && timingSafeEqual(mine, theirs);
}

@Controller('hooks')
export class GithubHookController {
  constructor(private readonly redis: RedisService, private readonly jenkins: JenkinsService) {}

  @Post('github')
  @HttpCode(200)
  async onPush(@Req() req: RawBodyRequest<Request>, @Headers() h: Record<string, string>) {
    const raw = req.rawBody as Buffer;
    if (!valid(raw, h['x-hub-signature-256'], process.env.HOOK_SECRET!)) {
      throw new ForbiddenException();                       // 伪造签名：403，且不产生构建
    }
    const p = JSON.parse(raw.toString('utf8'));
    if (h['x-github-event'] !== 'push' || p.deleted) return { skipped: true };

    const branch = String(p.ref || '').replace('refs/heads/', '');
    if (!['main', 'release'].includes(branch)) return { skipped: branch };

    const id = h['x-github-delivery'];
    const claimed = await this.redis.set(`hook:${id}`, '1', 'NX', 'EX', 600);
    if (!claimed) return { duplicate: true };               // 重投 / Redeliver

    // 只排队，不等构建；query 参数随后由 Generic Webhook Trigger 提取
    await this.jenkins.trigger({
      token: process.env.JENKINS_HOOK_TOKEN!,
      branch, sha: p.after, deliveryId: id,
    });
    return { queued: true, sha: p.after };                  // 10s 内返回 2xx
  }
}
Jenkinsfile 片段：Generic Webhook Trigger（字段细节以插件文档为准）triggers {
  GenericTrigger(
    genericVariables: [
      [key: 'ref', value: '$.ref'],
      [key: 'sha', value: '$.after']
    ],
    genericRequestVariables: [
      [key: 'branch',     regexpFilter: ''],
      [key: 'deliveryId', regexpFilter: '']
    ],
    token: 'story-main-deploy',
    causeString: 'Push $ref ($sha)',
    regexpFilterText: '$ref',
    regexpFilterExpression: '^refs/heads/(main|release/[0-9.]+)$'
  )
}

常见坑：NestJS 没开 rawBody: true 导致签名永不通过；把 X-GitHub-Event 拼错大小写（headers 在 Node 里全小写）；忽略 deleted / tag push；中继里同步等待构建导致 GitHub 超时后重投、越重投越重复；同一 delivery 重复部署；把 token 直接写进 Payload URL 又提交进文档；push feat/* 也部署了却没发现，因为过滤只做了一层。
自测
  1. GitHub 报「We couldn't deliver this payload: timeout」但 Jenkins 其实构建成功了，问题在哪？→ 中继没有在 10 秒内返回 2xx（多半在同步等构建 / 等 rollout）。应改为只验签 + 去重 + 触发排队，立刻返回。
  2. 用 refs/heads/release 新建分支会不会触发部署？→ 会收到一次 push 事件（created: true），若白名单含 release 就可能部署。要显式处理 created，并在 Jenkins 端再用正则与 when 兜底。

04

K8s 最小生产形态

读完你要能做到：把 W10 的 compose 四服务翻译成 K8s 对象，做一次不中断的滚动更新，并在出问题时按顺序定位、回滚。

  • 本地用 kind：单节点集群几分钟起，够练全部对象；生产用托管集群（EKS / ACK / TKE），本期不自建高可用控制面。kind 若要测 Ingress，创建集群时把 80/443 映射到 hostPort，并给 control-plane 打 ingress-ready=true 标签。
  • 对象与 compose 的对应：Deployment 管无状态副本（API / Web / Worker 各自一个），Service 提供稳定 ClusterIP + 标签选择器做负载均衡，Ingress 做域名 / 路径路由与 TLS 终止，ConfigMap 放非敏感配置，Secret 放敏感配置，Namespace 隔离环境。不要直接创建裸 Pod——它没有自愈与滚动更新。
  • 三类探针分工：startupProbe 保护慢启动（NestJS 连库 / 跑迁移）；readinessProbe 失败只从 Service endpoint 摘除，不重启容器；livenessProbe 失败才重启。readiness 只检查进程自身能否服务，不要查 DB / Redis——依赖一抖动会让所有副本同时被摘除，直接全站 503。
  • 资源声明：requests 决定调度到哪个节点，limits 决定 OOM / CPU 节流。内存 limit 必填，CPU limit 通常可不设（避免无谓节流）；不写 requests 的 Pod 在节点紧张时最先被驱逐。
  • 滚动与回滚：maxUnavailable: 0 + maxSurge: 1 保证更新期间不减容量（代价是集群要有 1 个副本的空余资源）；流水线用 rollout status --timeout 等待，失败时用 rollout history 找 revision、rollout undo --to-revision=N 恢复。
  • Secret 只是 base64，不是加密：不要把渲染后的 Secret YAML 提交到 Git。生产用 Sealed Secrets / External Secrets / 云 KMS，并开启 etcd 静态加密、用 RBAC 限制 get secrets。
  • 沿用 W10 的两个决定：SSE 路径要关 Ingress 的 proxy-buffering，否则进度条会卡住（W12 复盘里那个故障）；长任务 Worker 单独一个 Deployment，不要和 API 绑在一起扩缩容。
  • 有状态服务留在外面：MySQL / Redis 继续用托管实例或 W10 的 compose + 命名卷。放进 K8s 要处理 StatefulSet、PVC、备份、主从切换，复杂度远超本周收益。K8s 只承载无状态应用，这是对 W12 取舍的延续。

kind: Deployment
metadata:
  name: api
  namespace: story
spec:
  replicas: 2
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api }
    spec:
      containers:
      - name: api
        image: ghcr.io/you/story-api:<COMMIT_SHA>   # 由流水线 set image 覆盖
        ports:
        - containerPort: 3000
        envFrom:
        - configMapRef: { name: api-config }
        - secretRef:     { name: api-secret }
        startupProbe:
          httpGet: { path: /health/live, port: 3000 }
          failureThreshold: 30
          periodSeconds: 5
        readinessProbe:
          httpGet: { path: /health/ready, port: 3000 }
          periodSeconds: 5
        livenessProbe:
          httpGet: { path: /health/live, port: 3000 }
          periodSeconds: 10
        resources:
          requests: { cpu: 100m, memory: 128Mi }
          limits:   { memory: 512Mi }
---
apiVersion: v1
kind: Service
metadata:
  name: api
  namespace: story
spec:
  type: ClusterIP

部署、排错与回滚（bash，顺序即排查顺序）kubectl -n story apply -f deploy/base/
kubectl -n story get deploy,po,svc,ing                       # ① 先看整体状态
kubectl -n story describe pod <pod>                         # ② 事件：调度 / 拉镜像 / 探针
kubectl -n story logs deploy/api --previous                 # ③ 崩溃前一轮日志
kubectl -n story get events --sort-by=.lastTimestamp | tail -30
kubectl -n story rollout history deploy/api                 # ④ 发布历史（change-cause）
kubectl -n story rollout undo deploy/api --to-revision=3    # ⑤ 回滚
kubectl -n story rollout status deploy/api --timeout=180s

# 常见状态速查：
# ImagePullBackOff  镜像名/tag 错或私有仓库没配 imagePullSecrets
# CrashLoopBackOff  进程启动即退出，看 --previous 日志
# Pending           资源不足 / 没有可调度的节点 / PVC 未绑定
# OOMKilled         memory limit 太小，看 describe 的 Last State
# Running 但 503    readiness 未通过，Service 里没有 endpoint
常见坑：readinessProbe 里查数据库导致依赖抖动时全副本摘除；不给 startupProbe，慢启动被 liveness 反复杀；部署用 latest；maxUnavailable: 0 但节点没空余资源，滚动卡在 Pending；把 Secret YAML 提交上 Git；Worker 和 API 写在同一个 Deployment 导致扩缩容互相干扰；SSE 路径忘了关 proxy_buffering；把 kubeconfig 塞进 Jenkinsfile。
自测
  1. Pod 是 Running，接口却一直 503，先查什么？→ 查 readiness 是否通过、Service 是否有 endpoint（kubectl get endpoints），再看探针路径与 targetPort 是否和容器端口一致。
  2. 为什么镜像能回滚、数据库 schema 却不能一起回滚？→ 镜像是不可变产物，改指针即可；schema 变更已经写入数据，回滚应用可能与新结构不兼容。所以 W11 的 expand/contract 迁移必须与发布解耦、分两次上线。

运维闭环与取舍：什么时候才真的需要 K8s

读完你要能做到：不只「把服务跑起来」，还能说清配置、证书、观测、备份、回滚怎么闭环，以及这套东西对本项目的代价。

  • 镜像仓库：GHCR 或 Harbor，部署账号只读拉取、构建账号只写推送，分开授权；开镜像漏洞扫描（Trivy）与保留策略；部署只认 SHA tag。imagePullSecrets 按 namespace 配置，不要塞进每个 Deployment。
  • 配置与镜像分离：同一份镜像 + 不同 ConfigMap / Secret 跑 staging / production，避免「为每个环境构建一个镜像」。用 kustomize overlays 或 Helm values 管理差异，deploy/overlays/production/ 里流水线只改 image.tag 这一个字段。
  • TLS 自动化：W10 用 certbot 手工签发，这里换成 cert-manager + Ingress annotation 自动申请续期。证书到期必须有告警——自动续期失败是常见的「静默线上事故」。
  • 观测三件套：Prometheus + Grafana（P95、错误率、Pod 重启、OOM、队列积压）、集中日志（Loki / EFK，容器日志默认随 Pod 销毁而丢失）、Sentry 异常（W11 已接）。每条告警都要配一段可执行的 runbook，否则只是噪音。HPA 依赖 metrics-server 和合理的 requests，别一上来就开自动扩缩。
  • 发布策略的阶梯：滚动更新（默认够用）→ 蓝绿（双 Deployment 切 Service selector，回滚最快但占双倍资源）→ 金丝雀（Ingress 权重 / Argo Rollouts，需要指标判定）。无论哪种，数据库迁移走 W11 的 expand/contract 与发布解耦，因为镜像能回滚、schema 不能。
  • GitOps 是更清晰的边界：Argo CD 用拉模式，把 Git 当期望状态的单一真源，持续比对集群实际状态、检测并纠正手工 kubectl 造成的漂移。此时 Jenkins 只负责「构建镜像 + 更新清单仓库里的 tag」，不需要持有 kubeconfig，安全边界比推模式干净得多。推 / 拉两种模式可以并存演进。
  • 备份与可重建：延续 W11，DB 定时备份 + 恢复演练；所有部署清单、Jenkinsfile、Dockerfile 都在 Git，集群本身视为可丢弃；自建控制面才需要额外备份 etcd。RPO / 恢复耗时要有实测数字。
  • 取舍（写进 ADR）：单人 + 2C4G + 单体应用，K8s 控制面本身就要吃掉 1–2G 内存，还引入 Ingress / 证书 / 监控 / RBAC 一整套维护面，是净负担。W10 的 compose + W11 的 Actions 已经足够覆盖端到端交付。
出现这个信号再考虑迁移到 K8s
服务数 ≥ 3 且各自扩缩容节奏不同Deployment + HPA 的编排收益开始超过成本
需要多副本、自愈、不中断发布 SLA滚动更新 + 探针 + PDB 比手写脚本可靠
多人协作、需要环境隔离与权限边界Namespace + RBAC + GitOps 审计链
流量有明显波峰、需要弹性伸缩HPA / Cluster Autoscaler（前提是已有指标与资源基线）
仍只有 1 台小机器、1 个单体服务不要迁。继续 compose + 托管数据库，把时间花在功能与可观测上

常见坑：把 kubeconfig 当普通文件在流水线里传来传去；每个环境构建一个镜像导致「测过的镜像 ≠ 上线的镜像」；Secret 明文进 Git；证书自动续期失败无人知晓；HPA 没配 requests 根本不生效；告警一堆却没有 runbook；手工 kubectl edit 改了线上、Git 里没记录，下次发布被覆盖回去（漂移）；为了简历把项目硬迁到 K8s，结果 W12 的「为什么不用 K8s」答不上来。
自测
  1. Jenkins 推模式与 Argo CD 拉模式最本质的差别？→ 谁持有集群凭证、谁是期望状态真源。推模式由 CI 拿 kubeconfig 调 kubectl；拉模式由集群内控制器读 Git 自行同步，CI 不接触集群，且能检测漂移。
  2. 面试被问「你项目为什么用 / 不用 K8s」，怎么答？→ 先说约束（单人、单机、单体、Q1 目标是端到端交付），再给代价（控制面资源与运维面），最后给触发迁移的具体条件。说清条件比简单站队加分。
