01

契约驱动的请求层

读完你要能做到：后端改字段，前端编译期就报错；401 时自动刷新并重试，不丢用户操作。

  • 类型来源只有一个：openapi.json → openapi-typescript 生成 types.ts（W3 已建）。生成文件头注明「请勿手工编辑」，并在 CI 里校验生成结果与仓库一致。
  • 统一出口：所有请求走一个 request() 函数，集中处理 baseURL、Content-Type、token、错误码解包、超时与 AbortSignal。页面里不要散落裸 fetch。
  • 错误处理对齐 W1 的 { code, data, message }：HTTP 非 2xx 与业务 code 非 0 都转成同一个 ApiError，页面只处理一种错误对象。
  • 401 刷新队列：第一个 401 触发 refresh，其余并发请求挂起等待；刷新成功后统一重放，失败后清空会话跳登录。若每个请求各自 refresh，会撞上 W4 的轮换机制把令牌族全吊销。
  • 超时用 AbortController 主动取消，别只依赖浏览器默认（可能长达数分钟）。
web/src/api/request.ts（骨架）let refreshing: Promise<string | null> | null = null;

async function refreshOnce(): Promise<string | null> {
  if (!refreshing) {
    refreshing = doRefresh().finally(function () { refreshing = null; });
  }
  return refreshing;
}

export async function request<T>(path: string, init: RequestInit = {}): Promise<T> {
  const res = await fetch(import.meta.env.VITE_API_BASE + path, {
    ...init,
    headers: { 'Content-Type': 'application/json', ...authHeaders(), ...init.headers },
    signal: AbortSignal.timeout(8000),
  });
  if (res.status === 401) {
    const token = await refreshOnce();      // 并发请求共享同一次刷新
    if (token) return request<T>(path, init);
    redirectToLogin();
  }
  const body = await res.json();
  if (!res.ok || body.code !== 0) throw new ApiError(body.code, body.message, res.status);
  return body.data as T;
}
常见坑：生成的前端类型被手工改；每个 401 各刷一次 refresh；把 token 存 localStorage 被 XSS 读走；只判断 HTTP 状态码不判断业务 code；超时不取消导致请求堆积。
自测
  1. 为什么刷新要排队？→ 并发 401 各自刷新会触发轮换吊销，且产生多次无效请求。
  2. 为什么类型文件不能手改？→ 下次生成会被覆盖，且破坏「后端为唯一真源」的联动。

02

四态、防重复提交与进度恢复

读完你要能做到：任何页面在任何时刻都有明确反馈，用户不会面对空白或重复点击。

  • 每个数据视图都要有加载态、空态、错误态、正常态；错误态必须带「重试」动作，重试要保留原参数。
  • 表单提交：提交中禁用按钮 + 幂等键（W5）+ 成功后跳转 / 失效缓存；失败时恢复按钮并展示服务端 message，不要吞掉错误。
  • 上传页：分片进度按 W7 的服务端状态查询恢复，不依赖浏览器内存；超 5MB 分块，失败块单独重试。
  • 进度页：先查真值再订阅 SSE（W6），断线后重查一次；终态停止轮询 / 关闭 EventSource，避免后台无限请求。
  • 缓存失效：发布 / 删除 / 编辑后，让列表相关查询失效并重新拉取，否则会出现「提交成功但列表还是旧数据」。
页面状态机（伪代码）type ViewState<T> =
  | { kind: 'loading' }
  | { kind: 'empty' }
  | { kind: 'error'; message: string; retry: () => void }
  | { kind: 'ready'; data: T };

// 四种异常逐一演示：断网 / 500 / 401 / 超时
// 断网 → 错误态 + 重试；500 → 错误态 + 保留表单；
// 401 → 自动刷新后重放；超时 → 明确提示「请求超时」而非空白
常见坑：只有 loading 和 ready 两态；catch 里空实现；重试导致重复提交（缺幂等键）；页面卸载后 SSE 仍在跑；进度条依赖组件内存，刷新归零。
自测
  1. 为什么错误态必须带重试？→ 让用户可恢复而不必刷新整页，且能保留原参数与表单内容。
  2. 发布成功后列表没更新，问题在哪？→ 列表查询缓存未失效，需要主动重新拉取。

03

联调约定

读完你要能做到：本地一次配置好，之后不再为跨域、时间格式、分页字段反复扯皮。

  • 开发代理：Vite 的 server.proxy 把 /api 转发到 http://localhost:3000，浏览器看到的是同源请求，本地不必放宽后端 CORS。
  • 环境变量：前端只用 VITE_ 前缀变量，.env.local 不入库；生产 baseURL 由构建时注入，密钥绝不放前端。
  • CORS：生产后端只放行自己的域名（W8 白名单），配 credentials 时不能用通配符来源。
  • 统一约定：时间一律 UTC ISO 8601 字符串，由前端格式化本地时区；金额 / 大整数用字符串；分页固定 { items, total, page, pageSize }（W3 已定）。
  • 错误码表（W3）前端也要有一份映射，用于把 40301 之类翻译成用户能懂的提示。
vite.config.ts（节选）export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:3000',
        changeOrigin: true,
        rewrite: function (p) { return p.replace(/^\/api/, ''); },
      },
    },
  },
});
常见坑：本地靠 origin: '*' 绕过跨域，上线才发现坏；把后端密钥写进 VITE_ 变量（会被打进前端产物）；BigInt 直接 JSON 化丢精度；前后端各维护一份错误码表却不同步。
自测
  1. 为什么本地用代理而不是放宽 CORS？→ 本地同源更接近生产形态，也避免把宽松配置带上线。
  2. 为什么大整数要用字符串？→ JS Number 精度有限，BIGINT / 金额序列化会丢精度。
