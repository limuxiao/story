01

Entity、关联与 N+1

读完你要能做到：用一条 JOIN 查询取回文章与作者，而不是循环查库。

  • @Entity() 把类映射到表，@Column() 声明列，@PrimaryGeneratedColumn() 是自增主键；列名建议显式指定 name，避免 TS 属性名与数据库列名耦合。
  • 关联关系：@ManyToOne 是拥有外键的一方，@OneToMany 是反向侧（不产生列）。多对多可用 @ManyToMany 或显式中间表 Entity——主项目的 article_tags 建议显式建 Entity，方便后续加字段。
  • N+1：先查 N 篇文章，再对每篇查一次作者 = N+1 次 SQL。用 leftJoinAndSelect('a.user', 'u') 一次 JOIN 解决，或显式 relations。
  • find({ take, skip }) 适合简单分页；涉及条件、联表、聚合时用 QueryBuilder，并坚持参数化（setParameters），绝不字符串拼 SQL。
  • 事务用 dataSource.transaction(async (manager) => {...})，Service 层统一开；W2 已定过这条边界。
src/articles/article.entity.ts@Entity('articles')
export class Article {
  @PrimaryGeneratedColumn('increment', { type: 'bigint' })
  id: string;

  @Column({ length: 200 })
  title: string;

  @Column({ type: 'text' })
  body: string;

  @Column({ name: 'user_id', type: 'bigint' })
  userId: string;

  @ManyToOne(() => User, (user) => user.articles)
  @JoinColumn({ name: 'user_id' })
  user: User;

  @CreateDateColumn({ name: 'created_at' })
  createdAt: Date;
}
src/articles/articles.service.ts（分页 + 一条 JOIN）async list(query: ListArticlesDto) {
  const qb = this.repo.createQueryBuilder('a')
    .leftJoinAndSelect('a.user', 'u')
    .where('a.deleted_at IS NULL')
    .orderBy('a.created_at', 'DESC')
    .take(query.pageSize)
    .skip((query.page - 1) * query.pageSize);

  if (query.categoryId) {
    qb.andWhere('a.category_id = :categoryId', { categoryId: query.categoryId });
  }

  const [items, total] = await qb.getManyAndCount();
  return { items, total, page: query.page, pageSize: query.pageSize };
}
常见坑：开启 SQL 日志后才容易发现 N+1；leftJoinAndSelect 联表 + take/skip 在一对多关系上可能截断结果（TypeORM 会分两次查询，注意验证）；bigint 默认映射成字符串，别直接当 number 用；@Column({ nullable: true }) 与 DTO 的可选校验要对齐。
自测
  1. N+1 的「1」指什么？→ 第一次列表查询，之后每行再查一次关联数据。
  2. 为什么禁止字符串拼 SQL？→ 注入风险；QueryBuilder 的 setParameters 会做参数化。
  3. 事务应该放在哪一层？→ Service 层，Controller 只做委托。

02

DTO 校验与统一错误码

读完你要能做到：非法请求在 Pipe 层被挡住，业务冲突由 Service 抛业务异常，两者不混。

  • DTO 与 Entity 必须分离：DTO 描述「外部能传什么」，Entity 描述「库里存什么」。把 Entity 直接当 @Body() 会让客户端能改 id / userId。
  • class-validator 装饰器（@IsString() / @IsInt() / @MaxLength() / @IsOptional()）配合 ValidationPipe 生效；三个关键选项：whitelist 剥掉未声明字段、transform 做类型转换、forbidNonWhitelisted 遇到多余字段直接报错。
  • 边界：参数形状在 Pipe 校验，业务规则在 Service 判断。「邮箱格式」是前者，「作者只能改自己的文章」是后者。
  • 统一返回体沿用 W1 的 { code, data, message }；本周补一张错误码表（如 40001 参数错、40301 越权、40401 资源不存在、40901 冲突），业务异常类继承 HttpException，由全局 Filter 统一包装。
src/articles/dto/create-article.dto.tsexport class CreateArticleDto {
  @ApiProperty({ example: '我的第一篇文章' })
  @IsString()
  @MaxLength(200)
  title: string;

  @ApiProperty({ example: '正文内容' })
  @IsString()
  body: string;

  @ApiPropertyOptional({ example: 3 })
  @IsOptional()
  @Type(() => Number)
  @IsInt()
  categoryId?: number;
}
业务异常类 + 错误码表export const ErrorCode = {
  ARTICLE_NOT_FOUND: 40401,
  ARTICLE_FORBIDDEN: 40301,
} as const;

export class BizException extends HttpException {
  constructor(code: number, message: string, status = 400) {
    super({ code, message }, status);
  }
}

// Service 内
if (!article) throw new BizException(ErrorCode.ARTICLE_NOT_FOUND, '文章不存在', 404);
常见坑：只装 class-validator 不装 class-transformer；@Body() 用内联类型或 any，导致 ValidationPipe 完全不生效；把用户 ID 从请求体里取（应从 JWT 取，W4 补）；错误处理里泄露堆栈或 SQL 给客户端。
自测
  1. 为什么不能把 Entity 当 DTO？→ 外部可篡改 id / userId 等内部字段，造成越权与脏数据。
  2. whitelist 和 forbidNonWhitelisted 的差别？→ 前者静默剥离多余字段，后者直接抛错，联调期更推荐后者。

03

OpenAPI 作为单一真源

读完你要能做到：改 Entity / DTO 后，重新导出契约、生成前端类型，前端立刻编译报错。

  • @nestjs/swagger 的 SwaggerModule.createDocument() 生成 OpenAPI 文档对象；@ApiProperty() 补充 DTO 的字段说明与示例。
  • CLI plugin 能自动从 TS 类型推导 @ApiProperty，减少手写装饰器；但它依赖类型信息，泛型 / 联合类型仍需手工标注。
  • 把文档序列化成 openapi.json 提交进仓库，再用 openapi-typescript 生成前端 types.ts。这样后端改动 → 契约变化 → 前端类型检查失败，形成可验证的联动。
  • 契约要覆盖：路径、方法、请求 / 响应形状、状态码、错误码结构、分页参数。W8 的失败态清单会基于它补全。
src/swagger.ts（导出契约）import { NestFactory } from '@nestjs/core';
import { SwaggerModule, DocumentBuilder } from '@nestjs/swagger';
import { writeFileSync } from 'node:fs';
import { AppModule } from './app.module';

async function exportSpec() {
  const app = await NestFactory.create(AppModule, { logger: false });
  const config = new DocumentBuilder()
    .setTitle('Fullstack Lab API')
    .setVersion('1.0')
    .addBearerAuth()
    .build();
  const doc = SwaggerModule.createDocument(app, config);
  writeFileSync('./openapi.json', JSON.stringify(doc, null, 2));
  await app.close();
}
exportSpec();
package.json（契约脚本）{
  "scripts": {
    "spec": "ts-node src/swagger.ts",
    "types": "openapi-typescript ./openapi.json -o ../web/src/api/types.ts",
    "contract": "pnpm spec && pnpm types"
  }
}

本周验证动作：把 CreateArticleDto.title 改成 headline，跑 pnpm contract，前端列表页必须出现类型错误；改回来后恢复绿色。这个「故意改坏再修好」就是判据的验证方式。

常见坑：Swagger 文档只在开发期挂 UI、没导出 JSON 入库，前端拿不到真源；把 openapi.json 生成放在 CI 之后才跑，导致前端永远落后一个版本；生成的前端类型被手工修改（应在文件头注明「请勿编辑」）。
自测
  1. 为什么说契约是「单一真源」？→ 后端定义一次，前端类型与文档都由它生成，不再手工同步。
  2. CLI plugin 解决什么问题、有什么限制？→ 自动推导装饰器减少样板代码；复杂类型仍需 @ApiProperty 显式标注。
