01

密码哈希与令牌轮换

读完你要能做到：说清「密码怎么存、令牌怎么续期、旧令牌怎么作废」。

  • 密码只存哈希：bcrypt 或 argon2 自带加盐与计算成本，禁止 MD5/SHA 明文摘要、禁止自己实现加盐。登录时用恒定时间比较（库的 compare 已处理），并对「用户不存在」和「密码错」返回同一句话，避免用户枚举。
  • access + refresh 双令牌：access 短（如 15 分钟）放在 Authorization: Bearer；refresh 长（如 7 天）用于换新的 access。access 泄露窗口小，refresh 可被服务端吊销。
  • 轮换与吊销：每次刷新都作废旧 refresh、签发新 refresh（rotation），服务端存其哈希或版本号；检测到旧 refresh 被重用时，吊销该用户整条令牌族（提示可能被盗）。
  • 存放位置：SPA 用内存保存 access + HttpOnly/Secure/SameSite Cookie 保存 refresh，可缓解 XSS 窃取；纯移动端 / 服务端调用常用 Authorization 头。选一种并写进 ADR，W12 要能回答「为什么这么选」。
  • 密钥从 ConfigService 读，开发环境用 .env，生产走 Secrets；JWT 里只放 sub / roles 等必要声明，不放密码、手机号等敏感信息（payload 只是 Base64 编码，不是加密）。
src/auth/auth.service.ts（节选）async register(dto: RegisterDto) {
  const passwordHash = await argon2.hash(dto.password);
  return this.users.create({ email: dto.email, passwordHash });
}

async login(dto: LoginDto) {
  const user = await this.users.findByEmail(dto.email);
  // 用户不存在也做一次哈希比较，避免时序差异导致枚举
  const ok = user
    ? await argon2.verify(user.passwordHash, dto.password)
    : await argon2.verify(DUMMY_HASH, dto.password);
  if (!ok || !user) throw new BizException(40101, '邮箱或密码错误', 401);
  return this.issueTokens(user);
}
常见坑：把 JWT 当会话存敏感数据；refresh 不做轮换导致泄露后长期可用；token 存 localStorage 被 XSS 直接读走；JWT_SECRET 写死在代码或提交进仓库；忘记区分 401（未认证）与 403（已认证但无权限）。
自测
  1. 为什么要做 refresh 轮换？→ 每次刷新作废旧令牌，旧令牌重放可检测并吊销整条令牌族。
  2. JWT payload 能被加密吗？→ 默认只是签名 + Base64 编码，任何人可解码；敏感数据不能放。

02

Guards、角色与资源归属

读完你要能做到：让「A 的 token 改 B 的文章」在代码层与测试层都失败。

  • Guard 在请求进入 Controller 之前决定放行与否，返回值是布尔 / Promise / Observable；适合认证与粗粒度角色判断。
  • Passport 的 JwtStrategy 负责校验签名并把 payload 挂到 request.user；AuthGuard('jwt') 挂到需要登录的路由。
  • @Roles('admin') 是自定义装饰器，用 Reflect.defineMetadata 写元数据，RolesGuard 通过 Reflector 读出并与 request.user.roles 比对。
  • 关键：角色 ≠ 归属。「作者」这个角色不能证明这篇文章是他的。所有按 ID 操作的查询必须带当前用户条件：WHERE id = :id AND user_id = :currentUserId。只靠前端隐藏按钮或只校验登录态，就是典型的 IDOR（越权访问对象）漏洞。
  • 越权时对「不存在」和「不属于你」统一返回 404，避免通过状态码探测他人资源是否存在；若产品要求明确区分，用 403 但确认不泄露信息。
src/articles/articles.service.ts（资源归属）async updateOwned(articleId: string, userId: string, dto: UpdateArticleDto) {
  const article = await this.repo.findOne({
    where: { id: articleId, userId },   // 归属条件写进查询，不靠事后判断
  });
  if (!article) throw new BizException(40401, '文章不存在', 404);
  Object.assign(article, dto);
  return this.repo.save(article);
}
roles.guard.ts（骨架）@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(ctx: ExecutionContext): boolean {
    const required = this.reflector.getAllAndOverride<string[]>(ROLES_KEY, [
      ctx.getHandler(), ctx.getClass(),
    ]);
    if (!required) return true;
    const user = ctx.switchToHttp().getRequest().user;
    return required.some(function (role) { return user.roles?.includes(role); });
  }
}
常见坑：只在 Controller 里判断 if (article.userId !== user.id) 却先按 ID 全量查出（数据已出库，且容易漏分支）；把 userId 从请求体取（必须来自 JWT）；Guard 抛错没走全局 Filter，返回形状不一致；忘记给 /auth/* 加白名单造成登录也要求 token。
自测
  1. 为什么「角色正确」仍可能越权？→ 角色只证明身份类别，不证明资源归属；必须带 user_id 查询。
  2. Guard 与 Pipe 谁先执行？→ Guard 在 Interceptor / Pipe 之前，Pipe 紧接路由方法调用前。

03

Jest + Supertest 集成测试

读完你要能做到：写一条真实打接口的集成测试，并让它在 CI 里自动跑。

  • 分层：单测验证 Service 纯逻辑（mock 掉 Repository）；集成测试用 Supertest 真实发 HTTP 请求，走完整 Middleware → Guard → Pipe → Controller → Service → DB 链路。W4 重点做后者。
  • 测试库隔离：用独立 schema / database，绝不连开发库；beforeAll 建应用 + 跑 migration，afterAll 关闭连接。
  • 用例之间不互相污染：每个用例开事务、结束回滚，或用 factory 造数据并在 afterEach 清理。不要依赖用例执行顺序。
  • 用 NestFactory.create(AppModule) 后挂上与 main.ts 相同的全局 Pipe / Filter / Interceptor，否则测试环境和生产行为不一致。
  • CI 里加 pnpm test，顺序放在 typecheck 之后、build 之前；W8 会再加迁移与集成测试门禁。
test/articles.e2e-spec.ts（节选）describe('Articles (e2e)', () => {
  let app: INestApplication, userAToken: string, userBToken: string, articleId: string;

  beforeAll(async () => {
    const moduleRef = await Test.createTestingModule({ imports: [AppModule] }).compile();
    app = moduleRef.createNestApplication();
    // 与 main.ts 保持一致的全局管道 / 过滤器
    app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }));
    app.useGlobalFilters(new AllExceptionsFilter());
    await app.init();
  });

  afterAll(async () => { await app.close(); });

  it('A 不能修改 B 的文章', async () => {
    await request(app.getHttpServer())
      .patch('/articles/' + articleId)
      .set('Authorization', 'Bearer ' + userAToken)
      .send({ title: 'hacked' })
      .expect(404);   // 归属条件写进查询，查不到即 404
  });
});
常见坑：测试连了开发库导致数据被清空；测试里 mock 掉 Guard 使越权用例永远通过；用例共享同一个用户 / 文章 ID 造成顺序依赖；只在本地跑测试、CI 没接；beforeAll 里没等 app.init() 完成就发请求。
自测
  1. 为什么集成测试必须挂与 main.ts 相同的全局组件？→ 否则校验、异常包装行为与生产不一致，测试通过但线上出错。
  2. 越权用例为什么应该先失败再修？→ 证明用例真的能捕获问题，避免写出「永远绿」的假测试。
