01

同步 / 异步边界

读完你要能做到：判断一个操作该不该放进队列，并说清代价。

  • 同步适合：需要立刻拿到结果才能继续、耗时稳定且短（毫秒级）、失败必须当场告知用户的操作（登录、下单校验、参数校验）。
  • 异步适合：耗时超过网关 / 客户端超时、可重试、允许最终一致、需要削峰的操作（导出、生成报表、发邮件、转码、调用不稳定的第三方）。
  • 典型设计：接口只做参数校验 + 落一条任务记录 + 入队，立刻返回 202 Accepted 与 jobId；结果由用户随后查询或下载。
  • 代价要说得出：请求不再是「一次往返」，需要状态查询 / 进度推送、需要处理重复提交（W5 幂等键）、需要处理「任务成功但用户没看到」、队列积压时的可观测性。
  • 任务必须幂等：BullMQ 的「至少一次」语义意味着同一个 job 可能被执行多次（worker 崩溃、stalled 重新入队）。写文件、扣额度、发通知前都要先查状态机。
状态含义允许的流转
pending已入队，未开始→ running / failed
running执行中，含 progress 百分比→ succeeded / failed
succeeded完成，产物可下载终态，不再变更
failed重试耗尽→ pending（人工重试）
常见坑：把长任务塞在 HTTP 请求里等结果，网关一超时就前功尽弃；接口同步返回布尔值却没有任务记录，无法查询与重试；任务状态只存在 Redis / 内存里，进程重启进度全丢。
自测
  1. 为什么任务状态必须落库？→ 队列与 worker 都可重建，用户看到的进度与产物必须持久，刷新页面不能丢。
  2. 为什么任务要幂等？→ 至少一次投递下，崩溃 / stalled 会让同一 job 被重复执行。

02

Queue、Worker、重试与失败

读完你要能做到：配置重试退避，并让失败任务可查询、可手动重试。

  • Queue 负责入队与配置，Worker 负责消费，Job 是一次任务实例；同一队列名 + 同一 Redis 连接才能互通。
  • concurrency 控制单 worker 并行数；CPU 密集型（PDF 生成）别开太大，IO 密集型可适当提高。
  • attempts + backoff: { type: 'exponential', delay: 1000 } 做指数退避，避免失败任务立刻反复重试打爆依赖。
  • failed / stalled / completed 事件用于更新任务表与告警；不要只靠事件——事件丢失时，以任务表 + 定期扫描兜底。
  • Worker 应能安全中断：kill 后 BullMQ 会把 stalled job 重新入队，因此长任务内部要分段、可重入，并在每段落库进度。
  • 生产要限制队列长度 / 清理策略（removeOnComplete / removeOnFail），否则 Redis 内存会被历史 job 撑满。
src/exports/export.processor.ts（骨架）@Processor('export')
export class ExportProcessor extends WorkerHost {
  async process(job: Job<{ articleIds: string[]; taskId: string }>) {
    const { articleIds, taskId } = job.data;
    const total = articleIds.length;

    for (let i = 0; i < total; i++) {
      // 每段先查状态，保证重入时不重复写
      await this.tasks.markStepDone(taskId, articleIds[i]);
      await job.updateProgress(Math.round(((i + 1) / total) * 100));
      await this.tasks.setProgress(taskId, Math.round(((i + 1) / total) * 100));
    }
    const fileKey = await this.renderPdf(articleIds);
    await this.tasks.markSucceeded(taskId, fileKey);
  }
}

// 入队选项
await this.exportQueue.add('render', { articleIds, taskId }, {
  attempts: 3,
  backoff: { type: 'exponential', delay: 1000 },
  removeOnComplete: 100,
  removeOnFail: 50,
});
常见坑：在 job 里做超长不可中断的单体操作（kill 后从头重跑）；只更新 job.progress 不落库；把大对象（整篇文章内容）塞进 job data（应只传 ID）；没配 removeOnComplete 导致 Redis 膨胀；用同一 Redis DB 又做缓存又做队列且没设 maxmemory 策略。
自测
  1. stalled job 是什么？→ worker 失联 / 卡住超时后，BullMQ 判定任务未完成并重新入队。
  2. 为什么 job data 只放 ID？→ 队列数据要小且可序列化，大对象会增加 Redis 内存并让重试携带过期数据。

03

SSE 进度回传

读完你要能做到：前端进度条与实际状态一致，刷新页面后继续接着走。

  • SSE 是服务端 → 客户端的单向流，基于普通 HTTP，响应类型 text/event-stream；浏览器 EventSource 自带断线重连，并可通过 Last-Event-ID 续传。进度推送是单向场景，比 WebSocket 更轻。
  • NestJS 用 @Sse() 返回一个 RxJS Observable<MessageEvent>；长连接要处理心跳、客户端断开时取消订阅，避免泄漏。
  • 状态落库是判据：SSE 只是「通知」，真值在任务表。页面加载时先查一次 GET /tasks/:id 拿当前进度，再订阅 SSE 增量；断线后同样先重查再续订。
  • 兜底：SSE 被代理 / 浏览器环境阻断时，退化为每 2 秒轮询接口；轮询要有退避与终止条件（终态后停止）。
  • 鉴权：EventSource 不能自定义请求头，通常用 Cookie 或一次性 ticket 查询参数；不要把长期有效的 access token 放 URL（会进日志）。
src/exports/export.controller.ts（骨架）@Sse('tasks/:id/progress')
progress(@Param('id') taskId: string): Observable<MessageEvent> {
  return interval(1000).pipe(
    switchMap(() => from(this.tasks.findById(taskId))),
    map((task) => ({ data: { status: task.status, progress: task.progress } } as MessageEvent)),
    takeWhile((msg) => !['succeeded', 'failed'].includes(msg.data.status), true),
  );
}
web/src/pages/ExportProgress.ts（骨架）const current = await api.getTask(taskId);   // 先查真值，再订阅增量
setProgress(current.progress);
const es = new EventSource('/api/tasks/' + taskId + '/progress');
es.onmessage = function (e) {
  const data = JSON.parse(e.data);
  setProgress(data.progress);
  if (data.status === 'succeeded' || data.status === 'failed') es.close();
};
常见坑：把进度只放内存 / Redis，刷新即归零；Nginx 默认缓冲导致 SSE 不实时（需关 proxy_buffering）；连接不设心跳被代理超时断开；忘记在终态关闭 EventSource；进度百分比倒退。
自测
  1. 为什么选 SSE 而不是 WebSocket？→ 进度是单向推送，SSE 基于 HTTP、自带重连，实现与运维成本更低。
  2. 断线重连后如何保证进度不丢？→ 真值在任务表，重连先查一次当前状态再增量订阅。
