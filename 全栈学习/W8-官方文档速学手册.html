01

测试金字塔与 CI 门禁

读完你要能做到：说清三层各测什么，并把它们排进 CI 的正确位置。

  • 单测：只测 Service 的纯逻辑与错误分支，Repository 用 mock；跑得最快、数量最多，用于保护重构。
  • 集成测试：Supertest 走完整 HTTP 链路 + 真实测试库（W4 已建）；覆盖鉴权、幂等、契约形状这类「只有连起来才会错」的行为。
  • E2E：Playwright 跑一条主流程（登录 → 发文 → 导出 → 下载）即可，不追求页面全覆盖；它最慢最脆，放在最后。
  • 覆盖率看分支是否被触及，不迷信百分比；为凑数字写的断言毫无价值。
  • 门禁顺序：lint → typecheck → unit → migration → integration → build。前置步骤便宜且能快速失败；migration 单独跑一次是为了验证迁移脚本能在干净库上执行。
  • 失败禁止合并：在 GitHub 里把该 workflow 设为 required status check，并在 PR 模板里要求「本次改动的失败态是否覆盖」。
.github/workflows/ci.yml（W8 门禁版节选）      - run: pnpm lint
      - run: pnpm typecheck
      - run: pnpm test:unit
      - run: pnpm migration:run        # 干净库上验证迁移
      - run: pnpm test:e2e-api         # Supertest 集成
      - run: pnpm build
      - run: pnpm test:e2e-web         # Playwright 一条主流程
常见坑：测试连了开发库；用例共享数据导致顺序依赖；用 .only / .skip 提交进 CI；E2E 用固定 waitForTimeout 造成不稳定（应等具体元素 / 网络响应）；CI 里没跑 migration，迁移坏了要等部署才发现。
自测
  1. 为什么 migration 要在 CI 里单独跑？→ 验证迁移脚本能在干净库执行，把 schema 变更错误挡在部署前。
  2. 为什么 E2E 只跑一条主流程？→ 成本与脆弱性最高，覆盖关键路径收益最大。

02

Web 安全自查清单

读完你要能做到：对照 OWASP，逐项说出本项目当前的处理方式与残留风险。

项本项目做法自查动作
CORS白名单域名 + 明确 methods / headers，不用 origin: '*' 配 credentials用非白名单 Origin 发预检，确认被拒
CSRF若 refresh 放 Cookie，需 SameSite + CSRF token；纯 Bearer 头方案天然免疫确认方案与 ADR 一致
XSS输出转义、富文本白名单过滤、SVG/HTML 附件强制下载提交一段脚本内容看是否被当文本渲染
CSP限制脚本 / 样式来源，禁止 inline script响应头里有 Content-Security-Policy
SQL 注入QueryBuilder 参数化（W3）、禁止字符串拼 SQL用 ' OR 1=1 类输入测试
限流 / 枚举ThrottlerGuard（W5）、登录失败统一措辞（W4）短时间高频请求返回 429
依赖漏洞npm audit / pnpm audit 纳入门禁，定期更新CI 有依赖检查步骤
密钥.env 不入库、生产用 Secrets、日志脱敏（W5）仓库与日志全量搜索无凭据

建议把这张表变成仓库里的 SECURITY_CHECKLIST.md，每次发版前逐项打勾；W12 的复盘材料会用到它。

常见坑：开发期图省事开 origin: '*' 后忘记关；把 CSP 设成 unsafe-inline 等于没设；只查依赖漏洞不改；把 token 打进前端日志或错误上报。
自测
  1. 为什么 Bearer 头方案不易受 CSRF？→ 浏览器不会自动附带 Authorization 头，跨站请求无法借用凭证。
  2. origin: '*' 与 credentials 为什么冲突？→ 带凭证的跨域请求不允许通配符来源，且 wildcard 等于任意站点可读响应。

03

完整失败态与 Review 清单

读完你要能做到：为「发布文章」列出 ≥7 类失败态，并写进 PR 模板。

接口设计最容易被忽略的不是成功路径，而是失败路径。以「发布文章」为例，至少要覆盖：

  1. 参数错（缺 title / 超长 / 类型错）→ 400 + 40001
  2. 未登录 / token 过期 → 401
  3. 越权（改他人文章）→ 404（W4 归属查询）
  4. 业务冲突（重复发布 / 状态机不允许）→ 409
  5. 限流 → 429
  6. 依赖超时（DB / Redis / 队列不可用）→ 503 或降级，且日志可追踪
  7. 重复提交 / 并发重复请求 → 幂等返回首次结果（W5）
  8. 未知异常 → 500 + 统一错误体 + 日志留堆栈（W1 Filter）

PR 模板建议固定四问：改了什么 / 影响哪些接口与契约 / 新增或覆盖了哪些失败态 / 如何验证（命令与结果）。Review 时先问「这个改动最可能怎么坏」，再看代码。

本周验证：故意删掉一条归属条件、或提交一个类型错误、或写一个迁移却不写 down()，确认 CI 在对应步骤变红；修回后变绿。把截图 / 链接贴进复盘记录，这就是 G2 的证据。
