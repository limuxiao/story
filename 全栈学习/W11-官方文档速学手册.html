01

发布与回滚流水线

读完你要能做到：一次 push 触发完整发布，一键可回滚到上一个镜像 tag。

  • 顺序固定：lint / typecheck / test（W8 门禁）→ build 并推镜像，tag 用 commit SHA → migrate → deploy。用 SHA 而非 latest 才能精确回滚。
  • 环境区分：staging / production 用不同 job 或 environment，production 可加人工审批；所有凭据走 GitHub Secrets，绝不写进 yml 或 .env 入库。
  • 部署动作推荐「SSH 到服务器执行 docker compose pull && docker compose up -d」，服务器只拉镜像、不在上面构建；IMAGE_TAG 由 workflow 注入。
  • 回滚 workflow 用 workflow_dispatch 接收目标 tag，执行同一套部署脚本把 IMAGE_TAG 换回旧值；配好迁移的回滚脚本再回滚，否则新旧代码与 schema 不兼容。
  • 每次发布写一条 release 记录（版本、SHA、变更、迁移、回滚方式），W12 复盘直接引用。
.github/workflows/deploy.yml（骨架）on:
  push:
    tags: ['v*']
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t registry.example.com/app:${{ github.sha }} .
      - run: echo "${{ secrets.REGISTRY_TOKEN }}" | docker login registry.example.com -u ci --password-stdin
      - run: docker push registry.example.com/app:${{ github.sha }}
      - name: migrate
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.HOST }}
          username: ${{ secrets.USER }}
          key: ${{ secrets.SSH_KEY }}
          script: cd /srv/app && docker compose run --rm api pnpm migration:run
      - name: deploy
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.HOST }}
          username: ${{ secrets.USER }}
          key: ${{ secrets.SSH_KEY }}
          script: cd /srv/app && IMAGE_TAG=${{ github.sha }} docker compose up -d --no-build
常见坑：用 latest 部署导致无法回滚；把 SSH 私钥 / 数据库密码写进仓库；在服务器上构建镜像（资源紧张且不可复现）；只回滚应用不回滚迁移；发布后没有健康检查与失败自动中止。
自测
  1. 为什么镜像 tag 用 commit SHA？→ 可精确定位与回滚到任意一次构建，latest 无法区分版本。
  2. 回滚前为什么先处理迁移？→ 旧代码可能不兼容新 schema，需要先执行迁移的 down 脚本。

02

迁移安全与备份恢复

读完你要能做到：不中断服务地加一列，并从备份把库完整恢复出来。

  • expand / contract：加列分两阶段——先发布「兼容新旧 schema」的代码 + 加可空列的迁移（expand），确认稳定后再收紧约束、删除旧列（contract）。删列、改类型这类破坏性操作绝不和代码同一次发布。
  • 每次迁移都要有可执行的 down()；发布记录里写明「本次迁移如何回滚」。
  • 备份：mysqldump --single-transaction --routines --triggers 对 InnoDB 可在不停写的情况下拿一致性快照；用 crontab / systemd timer 定时执行，压缩后异地存放（对象存储 / 另一台机器），保留策略明确。
  • 恢复演练是判据：把备份恢复到临时实例，跑一遍迁移与几条关键查询，记录耗时。备份任务本身也要告警——最常见的故障是「备份天天跑，其实早失败了没人知道」。
  • 密钥、备份文件、生产数据都不进仓库；下载到本地分析要脱敏。
scripts/backup.sh#!/usr/bin/env bash
set -euo pipefail
STAMP=$(date +%Y%m%d-%H%M%S)
OUT="/srv/backups/db-$STAMP.sql.gz"
docker compose exec -T mysql \
  mysqldump --single-transaction --routines --triggers \
  -u root -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE" | gzip > "$OUT"
# 推到异地 + 清理 14 天前 + 失败时主动告警
aws s3 cp "$OUT" s3://my-backups/db/ && find /srv/backups -mtime +14 -delete
常见坑：只备份不恢复；备份和数据库放同一块盘（盘坏了两份都没）；在迁移里同时做结构变更和数据订正；down() 写了但从没执行过；备份脚本用明文密码且被写进仓库。
自测
  1. 为什么删列要拆成两次发布？→ 滚动更新期间新旧代码并存，直接删列会让旧版本报错。
  2. 备份恢复演练验证的是什么？→ 备份文件真的可用、恢复步骤可执行、耗时可估算。

03

观测与压测基线

读完你要能做到：给出 P95 数字，并判断瓶颈在 DB / 应用 / 网络哪一层。

  • 最小可观测三件：健康检查 /health（W1 已有，W10 被 Docker healthcheck 用）、错误上报（Sentry 之类，带 request-id 便于串联 W5 日志）、基础资源告警（CPU / 内存 / 磁盘 / 连接数 / 备份任务成败）。
  • 错误上报要脱敏：不传密码、token、完整请求体；生产 sourcemap 谨慎上传。
  • 压测：k6 或 autocannon 对 2–3 个关键接口（列表、详情、提交任务）跑一轮，记录 RPS、P95 / P99 延迟、错误率、慢 SQL 数量；把数字写进 README。
  • 瓶颈定位：P95 高 + DB CPU 高 + 慢查询多 → 查索引 / N+1（W2 / W3）；P95 高但 DB 空闲、应用 CPU 高 → 看序列化 / 同步计算 / GC；错误率随时长陡增 → 看连接池、队列积压、超时设置。
  • 别追求漂亮数字：目标是建立可比较的基线，日后每次优化都能对照。
k6/baseline.js（节选）import http from 'k6/http';
import { check } from 'k6';

export const options = {
  vus: 20,
  duration: '60s',
  thresholds: { http_req_failed: ['rate<0.01'] },
};

export default function () {
  const res = http.get('https://example.com/api/articles?page=1');
  check(res, { 'status 200': (r) => r.status === 200 });
}
常见坑：压测打到生产库写脏数据（应使用独立环境 / 只读接口）；只看平均响应时间不看 P95 / P99；并发数直接拉满没有梯度；没记录机器规格与数据规模，数字无法复现；告警规则从没触发验证过。
自测
  1. 为什么看 P95 而不是平均值？→ 平均值会掩盖长尾慢请求，P95 更接近真实用户体验。
  2. 压测发现 P95 高但 DB 空闲，先看什么？→ 应用侧 CPU、序列化、同步计算、连接池与 GC。
