01

多阶段 Dockerfile

读完你要能做到：构建出的镜像不含 devDependencies、不含源码与 .env，且以非 root 运行。

  • 多阶段：builder 阶段装全部依赖并编译，runtime 阶段只复制 dist + node_modules 生产依赖 + package.json，镜像体积与攻击面都大幅下降。
  • 层缓存：先复制 package.json / lockfile 装依赖，再复制源码；源码改动不会让依赖层失效。
  • .dockerignore 必须排除 node_modules、dist、.git、.env、日志，否则既拖慢构建又可能把密钥打进镜像。
  • 非 root 运行：用官方镜像自带的 node 用户；HEALTHCHECK 让编排层判断应用是否真的就绪。
  • 镜像 tag 锁到具体版本，别用 latest；数据库同理（mysql:8.0 / redis:7）。
DockerfileFROM node:22-alpine AS builder
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile
COPY . .
RUN pnpm build

FROM node:22-alpine AS runtime
WORKDIR /app
ENV NODE_ENV=production
COPY package.json pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile --prod
COPY --from=builder /app/dist ./dist
USER node
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD wget -qO- http://127.0.0.1:3000/health || exit 1
CMD ["node", "dist/main.js"]
常见坑：把 .env COPY 进镜像；builder 的 devDependencies 被带到 runtime；USER node 之后仍要写需要 root 权限的目录；healthcheck 探活路径本身也要鉴权（应放行 /health）。
自测
  1. 为什么先复制 package.json 再复制源码？→ 利用层缓存，改代码时不必重装依赖。
  2. 为什么运行时要用非 root？→ 容器逃逸 / 应用漏洞时缩小宿主机被影响的权限范围。

02

生产编排与数据边界

读完你要能做到：四个服务一次起齐，数据库端口不暴露公网，删容器重建数据还在。

  • depends_on 只管启动顺序；要等数据库真正可用，必须配 healthcheck + condition: service_healthy，否则应用常在初始化时连不上库。
  • 3306 / 6379 不出现在公网：要么完全不写 ports（只在 compose 内网互访），要么只绑 127.0.0.1；云控制台安全组与系统防火墙两层都要只放行 22 / 80 / 443。
  • 数据在命名卷里：docker compose down 保留数据，down -v 会连卷一起删。容器销毁不等于数据丢失，风险来自配置没做对。
  • 密钥走环境变量 / .env（不入库），生产由 Secrets 注入；restart: unless-stopped 配 log-opts 轮转，避免日志撑爆磁盘。
  • 机器规格 2 核 4G 起步，1G 内存跑 MySQL + Redis + NestJS + Nginx 容易被 OOM killer 杀掉；数据放独立数据盘，并开云主机自动快照兜底。
compose.prod.yml（节选）services:
  api:
    build: .
    restart: unless-stopped
    env_file: .env
    depends_on:
      mysql: { condition: service_healthy }
      redis: { condition: service_healthy }
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1:3000/health"]
      interval: 30s
      retries: 3
    logging:
      driver: json-file
      options: { max-size: "10m", max-file: "3" }

  mysql:
    image: mysql:8.0
    restart: unless-stopped
    env_file: .env
    volumes: ["mysql-data:/var/lib/mysql"]
    # 不写 ports：仅 compose 内网可达
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s
      retries: 5

  redis:
    image: redis:7
    command: ["redis-server", "--appendonly", "yes"]
    volumes: ["redis-data:/data"]

  web:
    image: nginx:alpine
    ports: ["80:80", "443:443"]
    volumes: ["./nginx.conf:/etc/nginx/conf.d/default.conf:ro", "./certbot:/etc/letsencrypt:ro"]
    depends_on: [api]

volumes:
  mysql-data:
  redis-data:
常见坑：把 ports: "3306:3306" 带到生产（等于数据库裸奔）；depends_on 当就绪用；改 data-root / 挂载点前没备份；把 .env 提交进仓库；误执行 down -v。
自测
  1. down 与 down -v 的区别？→ 后者连命名卷一起删，数据不可恢复。
  2. 为什么安全组和系统防火墙都要配？→ 两层独立，只配一层仍可能从另一层暴露端口。

03

Nginx 反代与 HTTPS

读完你要能做到：SPA 刷新不 404、上传体积不被默认限制挡住、SSE 实时推送、证书能自动续期。

  • proxy_pass 把 /api 转给 api 服务；try_files ... /index.html 是 SPA 前端路由刷新不 404 的关键。
  • client_max_body_size 默认 1MB，不调大会让 W7 的分片 / 附件上传直接 413；gzip 压缩文本资源。
  • SSE 要关 proxy_buffering off，否则 W6 的进度会被 Nginx 缓冲，前端看起来像卡住；同时把 proxy_read_timeout 调大。
  • HTTPS 用 certbot 签发（HTTP-01 或 DNS-01 挑战），配置自动续期并定期验证；HTTP 全量 301 到 HTTPS，可加 HSTS。
  • 安全响应头（W8 的 Helmet / CSP）可以在 Nginx 层统一补；不要重复设置造成冲突。
nginx.conf（节选）server {
  listen 80;
  server_name example.com;
  location / { return 301 https://$host$request_uri; }
}

server {
  listen 443 ssl;
  server_name example.com;
  ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
  client_max_body_size 20m;
  gzip on;

  location /api/ {
    proxy_pass http://api:3000/;
    proxy_set_header Host $host;
    proxy_set_header X-Request-Id $request_id;
    proxy_buffering off;              # SSE 必须
    proxy_read_timeout 300s;
  }
  location / {
    root /usr/share/nginx/html;
    try_files $uri $uri/ /index.html; # SPA fallback
  }
}
常见坑：证书续期没做定时任务或没验证；proxy_pass 末尾斜杠导致路径多一段 / 少一段；SPA fallback 漏配；SSE 被缓冲；上传 413 才想起 client_max_body_size。
自测
  1. SPA 刷新 404 怎么修？→ try_files 兜底到 /index.html，由前端路由接管。
  2. SSE 进度不实时，最可能哪里没配？→ Nginx proxy_buffering 未关闭。
