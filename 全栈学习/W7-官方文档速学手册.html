01

multipart、FileInterceptor 与流

读完你要能做到：把文件以流的方式落盘，而不是整块读进内存。

  • 浏览器上传用 multipart/form-data；NestJS 的 FileInterceptor 基于 multer，路由里用 @UploadedFile() 拿文件对象。
  • multer 的 limits.fileSize 是第一道大小闸门；fileFilter 做初筛，但真正的类型判定要读内容（见 03）。
  • 大文件必须用流：createReadStream / pipeline，避免 readFile 把整个文件读进内存导致 OOM。pipeline 还能正确传播错误并销毁流。
  • 本机开发用 diskStorage 落临时目录；生产建议对象存储。无论哪种，落盘文件名都要服务端重新生成（UUID / 哈希），不信任客户端文件名。
src/uploads/uploads.controller.ts（骨架）@Post('chunk')
@UseInterceptors(FileInterceptor('chunk', {
  limits: { fileSize: 5 * 1024 * 1024 },
}))
async uploadChunk(
  @UploadedFile() file: Express.Multer.File,
  @Body() dto: ChunkDto,
) {
  // 流式落盘，不把整块读进内存
  const dest = this.storage.chunkPath(dto.uploadId, dto.index);
  await pipeline(createReadStream(file.path), createWriteStream(dest));
  await this.uploads.markChunkReceived(dto.uploadId, dto.index, dto.hash);
  return { received: true };
}
常见坑：用 file.originalname 直接拼路径（路径穿越）；limits 不设导致单个请求打爆内存；流异常时没销毁句柄；临时文件不清理把磁盘写满。
自测
  1. 为什么大文件要用 pipeline？→ 背压控制 + 错误传播 + 自动销毁流，避免内存峰值与句柄泄漏。
  2. 为什么不能信 originalname？→ 客户端可控，可包含 ../ 或脚本后缀，必须服务端重新命名。

02

分片、断点续传与秒传

读完你要能做到：中断后重传不产生重复块，合并结果与一次性上传一致。

  • 客户端把文件切成固定大小块（如 5MB），每块带 uploadId、index、hash；服务端按 uploadId 建目录存块，并记录已接收的索引集合。
  • 续传：客户端先调 GET /uploads/:id/status 拿已接收索引，只补缺失块；服务端对重复块做幂等覆盖（W5 幂等思想）。
  • 合并：所有块齐全后按 index 顺序 pipeline 追加写入目标文件，校验整体 hash；合并任务应放进 W6 的队列异步做，避免请求超时。
  • 秒传：上传前先提交全文件 hash，若库中已有相同 hash 的文件记录且归属校验通过，直接复用，跳过传输。
  • 未完成的分片要有过期清理（TTL + 定时扫描），否则临时目录会无限增长。
合并（按序流式追加）async merge(uploadId: string, total: number) {
  const output = createWriteStream(this.storage.finalPath(uploadId));
  for (let i = 0; i < total; i++) {
    const part = this.storage.chunkPath(uploadId, i);
    await pipeline(createReadStream(part), output, { end: false });
  }
  output.end();
  await this.uploads.verifyHash(uploadId);   // 整体 hash 校验
  await this.uploads.cleanupChunks(uploadId);
}
常见坑：合并时不按 index 排序导致文件损坏；并发合并同一个 uploadId（需加锁 / 状态机）；块 hash 与整体 hash 都算但没校验；pipeline(..., { end: false }) 用错导致第一次就关闭输出流。
自测
  1. 续传为什么需要服务端状态？→ 客户端不知道哪些块已落盘且校验通过，必须由服务端给出已接收索引。
  2. 秒传的前提是什么？→ 全文件 hash 已存在且归属 / 权限校验通过，避免跨用户复用私有文件。

03

三重校验、存储与下载鉴权

读完你要能做到：解释为什么 Content-Type 不可信，并挡住三类攻击输入。

  • 三重校验：后缀白名单（最弱，可伪造）→ 声明的 MIME（同样可伪造）→ magic number（读文件头判断真实类型，如 file-type 库，最强）。三者取交集才放行。
  • 其他硬约束：大小限制、文件名随机化、存储目录不可执行、静态资源用独立域名 / 无 Cookie 域名、SVG / HTML 一律按附件下载而非内联渲染（防存储型 XSS）。
  • 预签名 URL 直传：服务端签发短期、限定 key 与 content-type 的 URL，客户端直传对象存储，避免文件流经应用服务器；本周可用本地实现替代，理解概念即可。
  • 下载二次鉴权：文件 key 不是公开 URL，请求先过 Guard 校验归属，再由服务端签发短期下载 URL 或流式回吐；W4 的资源归属原则在这里同样适用。
内容类型校验（伪代码）const ALLOW = new Set(['image/png', 'image/jpeg', 'application/pdf']);
const extOk = /\.(png|jpg|jpeg|pdf)$/i.test(originalName);
const meta = await fileType.fromFile(tempPath);        // 读 magic number
if (!extOk || !ALLOW.has(declaredMime) || !meta || !ALLOW.has(meta.mime)) {
  await unlink(tempPath);
  throw new BizException(40002, '文件类型不被允许', 400);
}
常见坑：只校验 Content-Type；把上传目录挂在 Web 根下且允许执行脚本；..%2f 编码后的路径穿越；预签名 URL 有效期过长或不限定 key；下载接口只校验登录不校验归属（IDOR）。
自测
  1. 伪装成 PNG 的 .php 怎么被拦？→ magic number 读出的真实类型不在白名单，且后缀 / MIME 不一致。
  2. 为什么上传目录要禁止执行？→ 即使脚本文件被传上来，Web 服务器也不会解析执行它。
