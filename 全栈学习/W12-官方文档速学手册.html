01

架构文档与 ADR

读完你要能做到：别人只读 README 和两张图，就明白系统怎么跑起来、为什么这样设计。

  • README 一条命令启动：前置条件（Docker / Node 版本）→ cp .env.example .env → docker compose up -d → 访问地址 → 如何跑测试。把 W10 的 bootstrap.sh 结果复用进来。
  • 架构图用 C4 Container 简化版：只画「浏览器 / Nginx / API / MySQL / Redis / 对象存储」及它们之间的调用，标注协议（HTTP / SQL / Redis / SSE）。不要一上来画类图。
  • ER 图复用 W2 的六张表，时序图专画 W6 的长任务链路（提交 → 入队 → Worker → 进度 SSE → 下载），这两张图是讲稿的主线。
  • Mermaid 可把图写进 Markdown 随仓库版本化，比贴图更易维护。
  • ADR 四段式：背景（当时要解决的问题）、选项（考虑过哪几种 + 各自代价）、决定（选了什么）、后果（带来什么限制 / 什么时候该重估）。本周至少写 2 份，例如「为什么用 compose 跑数据库而不是装本机 / 托管」和「为什么用 SSE 而不是 WebSocket」。
docs/adr/0001-db-deployment.md（模板）# ADR 0001：Q1 阶段数据库与缓存的部署方式

## 背景
单机 VPS、2C4G、单人开发，需要本机与线上环境一致，
且 Q1 目标是跑通端到端交付链路。

## 选项
1. 本机裸装 MySQL / Redis：版本易漂移，线上不一致。
2. 云托管 RDS + 托管 Redis：可靠性最好，但增加成本与运维范围。
3. Docker Compose 起容器：环境一致、一键重建、成本最低，
   但备份 / 高可用需自己承担。

## 决定
选 3，并强制命名卷持久化、端口不暴露公网、定时备份 + 恢复演练。

## 后果
单点风险由 Q1 接受；当出现多实例 / 跨可用区需求时，
重估并迁移到托管数据库。触发条件写进 Q2 检查点。

  2. README 的最低验收是什么？→ 一个没接触过项目的人能照着独立启动并跑通主流程。

02

复盘：时间线、5 Why 与踩坑故事

读完你要能做到：讲出两个真实故障，且每个都落到「根因 + 改进 + 验证方式」。

  • 时间线：按时间顺序记录「发生了什么 / 谁发现 / 怎么定位 / 怎么恢复」，只写事实不写猜测。
  • 5 Why：连续追问到可行动的根因。例：接口超时 → 慢查询 → 缺索引 → 迁移没评审 → 缺 CI 门禁 → 已在 W8 补上。停在「开发不小心」等于没复盘。
  • 改进项必须带验证方式：「加索引」要写「EXPLAIN 前后对比」；「加告警」要写「故意触发一次」。W8 / W11 的演练记录就是现成素材。
  • 准备两个故事：一次数据不一致（如 W5 缓存删除失败、W6 任务重复执行）、一次线上 / 部署故障（如 W10 Nginx 缓冲导致 SSE 不实时、证书续期失败）。
  • 复盘里也要写「哪些事做对了」：契约单一真源、先写失败用例、volume 与备份演练——这些是能体现工程判断的部分。
docs/postmortem/2027-01-sse-stall.md（结构）## 时间线
01-20 21:04 用户反馈导出进度条卡在 30%
01-20 21:12 查日志：任务表 progress 已到 100%，SSE 无推送
01-20 21:25 定位：Nginx 默认 proxy_buffering 缓冲了事件流
01-20 21:31 关闭缓冲并 reload，恢复

## 5 Why
为什么进度卡住 → 事件被缓冲 → 反代未针对 SSE 配置 → 本地无 Nginx 层
→ 本地与生产拓扑不一致 → 缺少「生产形态」的联调环境

## 改进与验证
1. nginx.conf 关 proxy_buffering（验证：进度 1s 内可见）
2. compose.prod.yml 加 web 服务（验证：本地走同一入口）
常见坑：复盘写成检讨书、追究个人；只列改进不写验证；把「以后更小心」当措施；没有量化影响时长 / 受影响请求数，讲稿里就缺可信度。
自测
  1. 5 Why 应该停在哪里？→ 停在能落地为「改进项 + 验证方式」的可行动根因。
  2. 为什么复盘要写「做对了什么」？→ 体现工程判断与可复用经验，避免只剩事故描述。

03

简历、讲稿与高频问答

读完你要能做到：30 分钟讲清项目，并答得上「为什么不用某个方案」。

  • STAR + 数字：情境 / 任务 / 动作 / 结果，结果必须带可核对的数字——QPS 或 P95（W11）、表数量与数据量（W2）、CI 步骤数（W8）、恢复演练耗时（W11）。
  • 30 分钟讲稿：架构与请求链（5min）→ 三个关键取舍（10min：compose 跑 DB、契约单一真源、SSE 而非 WebSocket）→ 一次真实故障与复盘（10min）→ 数据基线与后续演进（5min）。
  • 高频问答提前写逐字稿：索引最左前缀与 EXPLAIN；事务隔离级别与锁；幂等的四种手段；JWT 轮换与越权防护；线上 500 / 慢查询 / 容器起不来的排错顺序。
  • 三个「为什么不用」必须能答：为什么不用微服务 / K8s（Q1 单人不制造运维复杂度）、为什么单体够（Q1 目标是端到端交付而非高并发）、为什么选 MySQL 与 compose（生态成熟、本机与线上一致，代价是单点，触发什么条件时换托管）。
  • 材料要实际发出：投出第一份申请，或在内部发起一次跨端职责沟通。没发出就不算 G3 通过。
简历条目示例（改写自真实数字）独立设计并上线内容平台（NestJS + MySQL + Redis + Docker）
- 设计 6 张表与复合索引，10 万行数据下列表查询 P95 从 X ms 降至 Y ms（EXPLAIN 验证）
- 以 OpenAPI 为单一真源生成前端类型，字段变更在 CI 编译期暴露，联调返工降为 0
- 实现幂等发布与 BullMQ 长任务，kill worker 可恢复，进度刷新不丢
- 搭建 6 步 CI 门禁与发布/回滚流水线，完成备份恢复演练，RPO 与耗时已量化
常见坑：简历只写「使用了xx技术」没有结果与数字；讲稿按时间流水账讲功能；被问「为什么不用 X」时只会说「没学过」；作品没有公网可访问链接或 README 跑不起来。
自测
  1. 「为什么不用 K8s」怎么答才加分？→ 说清当前约束与代价，并给出触发迁移的条件，而不是简单否定。
  2. G3 为什么要求材料「已发出」？→ 转型的终点是身份落地，不只是作品完成。
