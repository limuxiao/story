01

Redis 数据类型与 Cache-Aside

读完你要能做到：给首页列表加上缓存，并说清什么时机删除它。

  • 常用类型：String（缓存单个对象 / 计数）、Hash（对象字段）、Set（去重、共同关注）、ZSet（排行榜 / 延迟队列的基础）。W6 的队列虽基于 Redis，但由 BullMQ 管理，不要自己用 List 造轮子。
  • 过期用 EXPIRE；加锁 / 抢占用 SET key value NX EX 60（单条命令原子）。老写法 SETNX 后再 EXPIRE 中间若进程崩溃会产生永不过期的死锁键。
  • Cache-Aside 读：先读缓存 → 命中返回 → 未命中读 DB → 回填缓存并设 TTL。写：先更新 DB，再删除缓存（不是更新缓存），避免并发写导致缓存里是旧值。
  • 三大问题：穿透（查不存在的 key，用空值缓存 + 短 TTL 或布隆挡）、击穿（热点 key 过期瞬间大量请求打到 DB，用互斥重建）、雪崩（大量 key 同时过期，TTL 加随机抖动）。
  • 缓存不是真源：「DB 写成功但删缓存失败」时，最实用的兜底是给缓存设较短 TTL 让脏数据自然过期，并给删除操作加重试 / 记录告警；不要在同一事务里同时操作 DB 与 Redis（两套存储没有分布式事务）。
src/articles/articles.service.ts（Cache-Aside）async getHomeList() {
  const key = 'home:articles:page1';
  const hit = await this.redis.get(key);
  if (hit) return JSON.parse(hit);

  const list = await this.list({ page: 1, pageSize: 20 });
  // TTL 加随机抖动，避免同一时刻大面积过期
  const ttl = 300 + Math.floor(Math.random() * 60);
  await this.redis.set(key, JSON.stringify(list), 'EX', ttl);
  return list;
}

async publish(articleId: string) {
  await this.repo.update(articleId, { status: 1 });           // 先写 DB
  await this.redis.del('home:articles:page1').catch(logWarn); // 再删缓存，失败留告警
}
常见坑：先删缓存再写 DB（并发读会把旧值回填）；缓存永不过期、无淘汰策略；把用户私有数据放进公共缓存 key；序列化 Date / BigInt 时静默丢精度；热点 key 无互斥导致重建风暴。
自测
  1. 写操作为什么删缓存而不是更新缓存？→ 并发写时更新顺序可能交错，缓存容易留下旧值；删除让下次读自然回填。
  2. SETNX + EXPIRE 两步有什么风险？→ 非原子，中间崩溃会产生永不过期的锁，应用 SET NX EX 一条命令。

02

限流与幂等设计

读完你要能做到：给「点赞 / 发布」做幂等，并用并发脚本证明它有效。

  • 限流：固定窗口用 INCR + EXPIRE（窗口边界可能有突刺），滑动窗口用 ZSet 记时间戳；NestJS 可直接挂 @nestjs/throttler 的 ThrottlerGuard，按路由配 limit / ttl。
  • 幂等 ≠ 防重复点击：前者保证「同一业务请求执行多次，结果一致」，后者是前端交互。要同时覆盖「用户连点两次」和「网络重试导致两个并发请求」。
  • 四种手段按可靠性排序：数据库唯一索引（最硬，W2 已建）→ INSERT ... ON DUPLICATE KEY UPDATE（冲突时改为更新）→ 幂等键 + SET key NX EX（先抢占再执行）→ 状态机（只允许 draft → published 单向流转）。
  • 幂等键来自客户端（如 Idempotency-Key 请求头）或业务唯一标识（user_id + article_id）；结果要缓存一份，重复请求直接返回首次结果，而不是重新执行。
  • 并发场景要验证「抢占成功但业务失败」：必须在异常路径释放幂等键，否则用户永远无法重试。
幂等发布（抢占 + 唯一索引双保险）async like(articleId: string, userId: string) {
  const idemKey = 'idem:like:' + articleId + ':' + userId;
  const claimed = await this.redis.set(idemKey, '1', 'NX', 'EX', 60);
  if (!claimed) return { duplicated: true };

  try {
    // 唯一索引 uk_article_user 兜住并发穿透
    await this.likeRepo.insert({ articleId, userId });
    await this.redis.incr('article:like:' + articleId);
    return { duplicated: false };
  } catch (e) {
    if (isDuplicateKeyError(e)) return { duplicated: true };
    await this.redis.del(idemKey);   // 业务失败要释放，允许重试
    throw e;
  }
}
常见坑：只在前端禁用按钮；幂等键过期时间短于业务执行时间；抢到键后业务失败不释放；用 SELECT ... 再 INSERT 做存在性判断（并发下必然重复，应交给唯一索引）；把限流当幂等用。
自测
  1. 为什么唯一索引比 Redis 抢占更可靠？→ 数据库约束是最后一道防线，Redis 键可能过期或被误删。
  2. 抢到幂等键后业务抛异常，应该怎么处理？→ 释放键并保留原始异常，否则用户被永久挡住。

结构化日志与 request-id

读完你要能做到：拿一个 request-id，捞出这次请求从进入到返回的全部日志。

  • 结构化：输出 JSON 而不是拼字符串，字段固定（ts / level / requestId / method / path / userId / durationMs / msg），才能被后续检索工具消费。
  • request-id 贯穿：中间件在请求进入时读取 X-Request-Id 或生成 UUID，挂到请求上下文（AsyncLocalStorage 或 Nest 的 ClsService），日志组件自动带上；响应头也回写该值，方便用户报障时提供。
  • 分级：error 需人工介入、warn 是可容忍异常（如缓存删除失败）、info 是关键业务节点、debug 只在开发开。
  • 脱敏：密码、token、Authorization、身份证、手机号一律不进日志；请求体只记字段名和长度，不记原文。W11 接错误上报时同样适用。
  • 日志要能串起「一次请求」，也要能串起「一次任务」——W6 的长任务把 jobId 作为第二个关联字段。
src/common/request-id.middleware.ts（骨架）@Injectable()
export class RequestIdMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    const id = String(req.headers['x-request-id'] || randomUUID());
    req['requestId'] = id;
    res.setHeader('X-Request-Id', id);
    logger.info({ requestId: id, method: req.method, path: req.path }, 'request in');
    res.on('finish', function () {
      logger.info({ requestId: id, status: res.statusCode }, 'request out');
    });
    next();
  }
}
常见坑：console.log 到处打印、没有关联字段；异步链路里 request-id 丢失（没用上下文传递）；把整个请求体打进日志导致密钥泄露；错误日志只有 message 没有堆栈和上下文。
自测
  1. 为什么日志要 JSON 化？→ 字段可被检索、聚合、告警，纯文本无法稳定解析。
  2. 响应头为什么回写 request-id？→ 用户报障时可直接提供该值，一次检索定位完整链路。
