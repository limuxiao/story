01

DDL、约束与表结构设计

读完你要能做到：为主项目画出六张表，并说清每个字段类型的选择理由。

1.1 类型选择的四条硬规则

  • 金额用 DECIMAL，不用 FLOAT / DOUBLE：浮点有精度误差，DECIMAL 是定点精确存储。
  • 时间用 DATETIME 或 TIMESTAMP：前者范围大且不受时区转换，后者占 4 字节、按时区显示；统一用 DATETIME + 应用层 UTC 更省心。
  • 字符集统一 utf8mb4：MySQL 的 utf8 是残缺的三字节实现，存不了 emoji。
  • 软删用 deleted_at DATETIME NULL：配唯一索引时注意 NULL 不参与唯一性判断，否则「删了再也建不回同名」。

1.2 约束是最后一道防线

主键（唯一且非空）、唯一索引（业务唯一性，如 users.email）、外键（引用完整性）、NOT NULL、默认值都建在库里，不要只靠应用层校验。W5 的幂等会直接复用唯一索引来挡重复写入。

1.3 范式与反范式

三范式解决冗余与更新异常；当「列表页要 JOIN 五张表」成为瓶颈时，才考虑冗余字段（如 articles.comment_count），并明确由谁维护一致性。W2 阶段的六张表先按范式设计，不做冗余。

主项目 ER：六张表users        id, email(uk), password_hash, name, created_at, deleted_at
articles     id, user_id(fk), category_id(fk), title, body,
             status, created_at, updated_at, deleted_at
categories   id, name(uk), slug(uk)
tags         id, name(uk)
article_tags article_id(fk), tag_id(fk)   -- 多对多中间表
comments     id, article_id(fk), user_id(fk), body, created_at
schema.sql（节选）CREATE TABLE articles (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id BIGINT UNSIGNED NOT NULL,
  category_id BIGINT UNSIGNED NOT NULL,
  title VARCHAR(200) NOT NULL,
  body TEXT NOT NULL,
  status TINYINT NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted_at DATETIME NULL,
  PRIMARY KEY (id),
  KEY idx_user_created (user_id, created_at),
  KEY idx_category_status_created (category_id, status, created_at),
  CONSTRAINT fk_articles_user FOREIGN KEY (user_id) REFERENCES users (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
常见坑：用 VARCHAR(255) 兜所有字符串（浪费索引长度）；外键列类型与主键不一致导致建表失败；软删字段与唯一索引冲突；自增 ID 用有符号 BIGINT；所有表都加 updated_at 却没人维护。
自测
  1. 为什么金额不能用 FLOAT？→ 浮点二进制表示有精度误差，DECIMAL 是精确定点数。
  2. 软删 + email UNIQUE 会有什么问题？→ 被软删的行仍占用唯一值，同邮箱无法重建；要么物理删，要么把 deleted_at 纳入唯一索引。

02

查询、分页与事务

读完你要能做到：写出列表页的 JOIN 查询，并说清事务边界放在哪一层。

  • INNER JOIN 只保留两表都匹配的行；LEFT JOIN 保留左表全部行，右表无匹配补 NULL——统计「文章 + 评论数」必须用 LEFT，否则零评论文章会消失。
  • WHERE 过滤行，HAVING 过滤分组后的结果；GROUP BY 之后 SELECT 的列要么是分组键，要么是聚合函数。
  • LIMIT offset, size 在深分页时越翻越慢（要扫描并丢弃 offset 行）；大数据量改用游标分页：WHERE created_at < :last ORDER BY created_at DESC LIMIT 20。
  • ACID：原子性、一致性、隔离性、持久性。事务边界放在 Service 层（dataSource.transaction()），不要放在 Controller，也不要一个请求开多个短事务。
  • 隔离级别：读未提交 / 读已提交 / 可重复读（InnoDB 默认）/ 串行化。重点理解脏读、不可重复读、幻读分别在哪一级被挡住。
  • SELECT ... FOR UPDATE 对命中行加排他锁，必须在事务内使用；W5 的库存 / 状态机场景会用到，本期只做认知。
列表页查询（含零评论文章）SELECT a.id, a.title, a.created_at,
       COUNT(c.id) AS comment_count
FROM articles a
LEFT JOIN comments c ON c.article_id = a.id
WHERE a.status = 1 AND a.deleted_at IS NULL
GROUP BY a.id, a.title, a.created_at
ORDER BY a.created_at DESC
LIMIT 20;
TypeORM 事务边界（Service 层）await this.dataSource.transaction(async (manager) => {
  const article = manager.create(Article, { title, body, userId });
  await manager.save(article);
  await manager.save(ArticleTag, tags.map((tagId) => ({ articleId: article.id, tagId })));
  return article;
});
常见坑：LEFT JOIN 后在 WHERE 里对右表列加条件，会把它退化成 INNER JOIN；COUNT(*) 与 COUNT(col) 对 NULL 的处理不同；事务里做远程调用 / 发邮件导致长事务；SELECT ... FOR UPDATE 没走索引会锁全表。
自测
  1. 零评论文章为什么会被 INNER JOIN 丢掉？→ 没有匹配的 comments 行，连接结果为空，需 LEFT JOIN。
  2. 深分页为什么慢，怎么改？→ offset 需扫描丢弃前 N 行；改用基于 created_at / id 的游标分页。

03

索引与 EXPLAIN

读完你要能做到：拿一条慢 SQL，用 EXPLAIN 判断瓶颈并给出索引方案。

  • InnoDB 用 B+ 树：聚簇索引的叶子节点直接存整行数据，二级索引叶子存主键值（所以二级索引查询常要「回表」）。
  • 最左前缀：复合索引 (a,b,c) 能服务 a、a+b、a+b+c 的等值条件；跳过 a 只用 b 或 c 用不上。范围条件之后的列无法继续用索引排序。
  • WHERE a=1 AND b>2 ORDER BY c 用 (a,b,c)：a 等值定位、b 范围过滤，b>2 之后 c 已无法用于查找，但 (a,b,c) 仍是覆盖该查询形状的最佳选择。
  • 覆盖索引：所需列都在索引里，无需回表，Extra 会显示 Using index。
  • EXPLAIN 重点看：type（system > const > eq_ref > ref > range > index > ALL）、key（实际用的索引）、rows（预估扫描行数）、Extra（Using filesort / Using temporary 是要优化的信号）。
  • 索引不是越多越好：每个索引都增加写入成本与磁盘占用；低区分度列（如 status）单独建索引通常没用，但放进复合索引的前缀之外可能有价值。
对比实验（本周必须做一次）EXPLAIN SELECT id, title FROM articles
WHERE category_id = 3 AND status = 1
ORDER BY created_at DESC LIMIT 20;

-- 加索引前后各跑一次，记录 type / key / rows / Extra
CREATE INDEX idx_cat_status_created
  ON articles (category_id, status, created_at);

EXPLAIN SELECT id, title FROM articles
WHERE category_id = 3 AND status = 1
ORDER BY created_at DESC LIMIT 20;

灌 10 万行再对比才有意义——空表时优化器可能直接选全表扫描，看不出差别。EXPLAIN ANALYZE（MySQL 8.0.18+）会真实执行并给出实际耗时，比只看估算更准。

常见坑：对索引列用函数或隐式类型转换（WHERE DATE(created_at)=...、字符串传数字）导致索引失效；LIKE '%abc' 前置通配符用不上索引；只看 rows 不看 Extra；在测试库用 100 行数据下结论。
自测
  1. 复合索引 (a,b,c) 能服务 WHERE b=1 AND c=2 吗？→ 不能，违反最左前缀。
  2. Using filesort 一定是坏事吗？→ 不一定，小结果集排序可接受；但配合大 rows 与深分页就是要优化的信号。

04

Migrations 与测试数据

读完你要能做到：用迁移建库、回滚、再重建，并用 seed 灌出可压测的数据量。

  • 迁移文件是版本化的 schema 变更脚本，必须入库、按序执行、不可逆操作要配反向脚本；禁止直接改生产库表结构。
  • TypeORM 常用命令：migration:generate（对比 Entity 与库生成差异）、migration:run、migration:revert。生成后必须人工复核，自动生成的 SQL 可能包含意外的 DROP。
  • 每次迁移都要能回滚；W11 会要求「向前兼容的 expand / contract 两阶段」，W2 先养成写 down() 的习惯。
  • seed 用批量插入（每批 1000 行）而不是逐行 save()，10 万行才不会跑十分钟。
package.json（scripts 节选）{
  "scripts": {
    "migration:generate": "typeorm-ts-node-commonjs migration:generate ./src/migrations/init -d ./src/data-source.ts",
    "migration:run": "typeorm-ts-node-commonjs migration:run -d ./src/data-source.ts",
    "migration:revert": "typeorm-ts-node-commonjs migration:revert -d ./src/data-source.ts",
    "seed": "ts-node src/database/seed.ts"
  }
}
迁移文件骨架export class InitSchema1700000000000 implements MigrationInterface {
  public async up(queryRunner: QueryRunner): Promise<void> {
    await queryRunner.query(`CREATE TABLE articles (...)`);
  }
  public async down(queryRunner: QueryRunner): Promise<void> {
    await queryRunner.query(`DROP TABLE articles`);
  }
}
常见坑：直接改已执行过的迁移文件（队友与 CI 会不一致）；Entity 与数据库不同步就反复 generate；synchronize: true 带到生产（会静默改表）；迁移里塞数据订正却不写回滚。
自测
  1. 为什么生成的迁移必须人工复核？→ 自动对比可能把重命名识别为 DROP + ADD，导致数据丢失。
  2. 为什么 synchronize 不能上生产？→ 应用启动时自动同步 schema，等同于未经评审的在线 DDL。
