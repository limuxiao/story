01

HTTP 语义与 REST 设计

读完你要能做到：给「用户 / 文章」设计出方法、路径、状态码都站得住脚的接口，并解释为什么这样选。

1.1 方法：安全、幂等、可缓存是三个不同概念

MDN 把请求方法按语义区分，W1 只需要抓住三个词：安全（不改变服务器状态）、幂等（重复执行一次和多次效果相同）、可缓存。「安全」不等于「幂等」，幂等也不等于「响应完全相同」。

方法语义安全幂等W1 里的用法
GET取资源表示是是用户列表、用户详情；不带请求体
HEAD同 GET 但无响应体是是健康检查探活可选用
POST提交实体，常引发状态变化否否新建用户；重复提交会产生两条数据，这正是 W5 幂等要解决的问题
PUT整体替换目标资源否是全量更新，客户端需提供完整表示
PATCH局部修改否通常否只改某几个字段
DELETE删除指定资源否是重复删除结果一致（第二次返回 404 也符合语义）
OPTIONS查询通信选项是是浏览器 CORS 预检自动发起，W8 配白名单时才会显式接触

状态码按 RFC 9110 分五类，W1 先记住「谁的责任」：2xx 成功、4xx 客户端错、5xx 服务端错。

码含义本周用在哪
200 OK请求成功查询、更新的默认响应
201 Created已创建资源POST 新建用户（NestJS 默认 POST 就是 201）
204 No Content成功但无响应体DELETE 成功可选
400 Bad Request参数 / 格式错ValidationPipe 拦截后的返回
401 Unauthorized未认证W4 才用；注意名字容易和 403 混淆
403 Forbidden已认证但无权限W4 才用
404 Not Found资源不存在查无此用户
409 Conflict资源状态冲突W5 幂等 / 唯一键冲突
500 Internal Server Error服务端未处理异常全局 ExceptionFilter 兜底

1.2 请求头：本周只需要四个

  • Content-Type: application/json —— 告诉服务端请求体格式；POST / PUT 必带。
  • Authorization: Bearer <token> —— 承载凭证；W4 接 JWT，本周只需知道位置。
  • Accept —— 客户端期望的响应类型。
  • Idempotency-Key —— 约定性请求头（非 HTTP 标准），W5 做幂等时会用到，先留个印象。

1.3 REST 命名约定（团队共识，不是协议强制）

  • 用复数名词表示集合：/users、/users/:id，不要在路径里塞动词（/getUser 是反例）。
  • 嵌套不超过两层：超过就改用查询参数或独立资源。
  • 筛选、排序、分页走查询参数：/articles?page=2&pageSize=20&sort=-createdAt。
  • 动作型需求（如导出）无法套 CRUD 时，用子资源表达：POST /exports，W6 的长任务会这么设计。

本周三条接口 + 健康检查：

方法路径成功码说明
GET/users200列表（W3 才加分页）
GET/users/:id200 / 404详情；:id 用 ParseIntPipe 转数字
POST/users201新建；请求体走 DTO 校验
GET/health200返回服务状态，W10 会被 Docker healthcheck 使用
常见坑：把 GET 用来改数据；用 POST 承载所有操作；404 和 403 混用（后者会泄露资源存在性）；返回 200 却在响应体里塞 { success: false }——HTTP 状态码和业务码要各司其职，W1 的统一返回体只包装数据，不取代状态码。
自测
  1. 为什么说 POST 非幂等？→ 重复提交会产生多条资源，W5 需要用唯一键 / 幂等键兜住。
  2. DELETE 一个不存在的资源，第二次返回 404 算不算违反幂等？→ 不算，幂等看服务器最终状态，不是每次响应完全相同。
  3. /users/3/articles?status=draft 体现了哪两条约定？→ 复数名词 + 两层嵌套 + 筛选走查询参数。

02

NestJS 分层与依赖注入

读完你要能做到：不看模板新建一个 Module，并说清「哪一层不该写 SQL」。

2.1 四个角色，各司其职

角色职责不该做的事
Module用 @Module() 声明一组内聚能力；Nest 从根模块出发构建应用图，解析模块与 provider 之间的依赖不写业务逻辑
Controller处理入站请求、返回响应；装饰器把类和方法挂到路由表上，路径前缀写在 @Controller('users') 上避免重复不写业务规则、不写 SQL
Provider / Service加 @Injectable() 的类，可被注入为依赖；服务、仓库、工厂、helper 都是 provider。复杂任务由 Controller 委托给它不直接拼 HTTP 响应
Repository数据访问层，W2 之后由 TypeORM Repository 承担只有这一层碰 SQL / ORM

@Module() 的四个属性必须能背出来：imports（导入别的模块导出的 provider）、controllers（本模块要实例化的控制器）、providers（由注入器实例化、至少在本模块内可共享）、exports（把本模块 provider 暴露给别的模块）。Provider 默认单例，要跨模块用必须先 exports 再在对方 imports。

2.2 最小可运行骨架

src/users/users.service.tsimport { Injectable, NotFoundException } from '@nestjs/common';

@Injectable()
export class UsersService {
  private readonly users = [{ id: 1, name: 'Ada' }];

  findAll() {
    return this.users;
  }

  findOne(id: number) {
    const user = this.users.find(function (u) { return u.id === id; });
    if (!user) throw new NotFoundException('User not found');
    return user;
  }

  create(dto: { name: string }) {
    const user = { id: Date.now(), name: dto.name };
    this.users.push(user);
    return user;
  }
}
src/users/users.controller.tsimport { Body, Controller, Get, Param, ParseIntPipe, Post } from '@nestjs/common';
import { UsersService } from './users.service';

@Controller('users')
export class UsersController {
  constructor(private readonly usersService: UsersService) {}

  @Get()
  findAll() {
    return this.usersService.findAll();
  }

  @Get(':id')
  findOne(@Param('id', ParseIntPipe) id: number) {
    return this.usersService.findOne(id);
  }

  @Post()
  create(@Body() dto: { name: string }) {
    return this.usersService.create(dto);
  }
}
src/users/users.module.tsimport { Module } from '@nestjs/common';
import { UsersController } from './users.controller';
import { UsersService } from './users.service';

@Module({
  controllers: [UsersController],
  providers: [UsersService],
  exports: [UsersService],
})
export class UsersModule {}
src/app.module.tsimport { Module } from '@nestjs/common';
import { ConfigModule } from '@nestjs/config';
import { UsersModule } from './users/users.module';

@Module({
  imports: [
    ConfigModule.forRoot({ isGlobal: true, envFilePath: '.env' }),
    UsersModule,
  ],

export class AppModule {}

依赖注入的关键就是那行构造函数：constructor(private readonly usersService: UsersService)。Nest 运行时按类型 token 到容器里找实例并「接线」，你只声明「我要什么」，不自己 new。这也是判据里「Provider(DI)」的含义。

2.3 装饰器速查（本周只需这些）

装饰器作用
@Controller('users')类级路由前缀
@Get() / @Post()方法级 HTTP 方法与子路径
@Param('id', ParseIntPipe)取路径参数并转换为数字
@Body() / @Query()取请求体 / 查询参数
@HttpCode(200)覆盖默认状态码（POST 默认是 201）
@Injectable()把类标记为可注入的 provider
常见坑：把 Service 写进 controllers 数组，或忘记在 providers 注册就注入（会报 Nest can't resolve dependencies）；跨模块用 provider 忘了 exports；在 Controller 里直接连数据库——W2 接 TypeORM 后这类代码会立刻失控。
自测
  1. @Module() 四个属性分别是什么？→ imports / controllers / providers / exports。
  2. 为什么 Service 要加 @Injectable()？→ 让 Nest 把它登记为可注入 provider，才能被构造函数注入解析。
  3. 哪一层可以写 SQL？→ 只有 Repository / 数据访问层（W2 起由 TypeORM 承担）。

03

请求生命周期与统一返回体

读完你要能做到：口述完整调用链，并用一个 Interceptor + 一个 ExceptionFilter 把所有响应包成同一种形状。

3.1 官方给出的请求顺序

Nest 官方把一次请求描述为：请求先经过 middleware → guards → interceptors（进入方向） → pipes → controller 路由处理 → service，返回时再沿 interceptors 的返回路径生成响应；任何环节抛出的未处理异常，由 exception filters 层兜底。中间件按「全局 → 模块绑定」的顺序执行。

环节职责W1 是否实现
Middleware最早执行，适合放 request-id、原始日志本期跳过（W5 补）
Guards决定请求能否进入（鉴权 / 角色）本期跳过（W4 补）
Interceptors包裹方法执行前后，可转换响应、加缓存、记耗时做：统一成功返回体
Pipes紧接在路由方法调用前，做 transformation（如字符串转整数）与 validation（不合法就抛异常）做：ParseIntPipe / ValidationPipe
Controller → Service委托业务逻辑做
Exception filters内置全局过滤器已处理 HttpException 及其子类；无法识别的异常默认返回 {"statusCode":500,"message":"Internal server error"}做：自定义换取统一错误体

规划文档里要求口述的「请求 → 中间件 → Guard → Pipe → Controller → Service → Repository」是业务视角的精简链；完整版要记得前后各有一层 Interceptor 包裹，以及异常时由 Filter 接管。面试时能把两者都讲出来最稳。

3.2 统一返回体：成功用 Interceptor，失败用 Filter

约定形状：{ code, data, message }。成功后置包装交给 Interceptor，异常包装交给 Filter，Controller 里绝不手写 try/catch 拼装。

src/common/transform.interceptor.tsimport { CallHandler, ExecutionContext, Injectable, NestInterceptor } from '@nestjs/common';
import { Observable, map } from 'rxjs';

export type ApiResponse<T> = { code: number; data: T; message: string };

@Injectable()
export class TransformInterceptor<T> implements NestInterceptor<T, ApiResponse<T>> {
  intercept(ctx: ExecutionContext, next: CallHandler<T>): Observable<ApiResponse<T>> {
    return next.handle().pipe(map(function (data) {
      return { code: 0, data: data, message: 'ok' };
    }));
  }
}
src/common/all-exceptions.filter.tsimport {
  ArgumentsHost, Catch, ExceptionFilter, HttpException,
  HttpStatus, Logger,
} from '@nestjs/common';

@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  private readonly logger = new Logger(AllExceptionsFilter.name);

  catch(exception: unknown, host: ArgumentsHost) {
    const res = host.switchToHttp().getResponse();
    const isHttp = exception instanceof HttpException;
    const status = isHttp
      ? exception.getStatus()
      : HttpStatus.INTERNAL_SERVER_ERROR;
    const detail = isHttp ? exception.getResponse() : 'Internal server error';

    // 未知异常必须留痕，不能被过滤器悄悄吞掉
    if (!isHttp) this.logger.error(exception);

    res.status(status).json({ code: status, data: null, message: detail });
  }
}
src/main.tsimport { NestFactory } from '@nestjs/core';
import { ValidationPipe } from '@nestjs/common';
import { AppModule } from './app.module';
import { TransformInterceptor } from './common/transform.interceptor';
import { AllExceptionsFilter } from './common/all-exceptions.filter';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }));
  app.useGlobalInterceptors(new TransformInterceptor());
  app.useGlobalFilters(new AllExceptionsFilter());
  await app.listen(process.env.PORT ?? 3000);
}
bootstrap();

本周验证动作：在 findOne 里抛一个 NotFoundException，用 curl -i 确认状态码是 404 且响应体符合约定；再抛一个普通 Error，确认返回 500、日志里有堆栈。这两步就是规划文档 W1 练习里的「故意抛业务异常，确认全局 ExceptionFilter 转成统一返回体」。

常见坑：ValidationPipe 不设 transform: true 时 @Param('id') 拿到的是字符串；whitelist: true 会静默剥掉 DTO 未声明字段，W3 会补 forbidNonWhitelisted；Pipe 运行在异常区内，Pipe 抛出的异常会被 Filter 接到，所以别在 Pipe 里自己吞异常；自定义 @Catch() 不指定类型会接管全部异常，务必保留日志。
自测
  1. Pipe 和 Interceptor 都在方法前后运行，区别是什么？→ Pipe 只处理方法参数（转换 / 校验），Interceptor 包裹整个执行流并可改写响应。
  2. 内置全局异常过滤器对不认识的异常返回什么？→ statusCode 500 + "Internal server error" 的 JSON。
  3. 为什么未知异常必须记日志？→ 自定义 Filter 接管全部异常后，不记日志会把线上故障变成无声失败。

4.1 TypeScript strict 与三条脚本

W1 的目标不是学 TS 类型体操，而是把 noImplicitAny、strictNullChecks 等检查打开，让 W3 的 DTO / 契约生成不返工。strict: true 会一并启用这一组检查；noEmit 用于纯类型检查。

tsconfig.json（关键项）{
  "compilerOptions": {
    "module": "commonjs",
    "target": "ES2022",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "outDir": "dist",
    "sourceMap": true
  },
  "include": ["src/**/*.ts"]
}
package.json（scripts 节选）{
  "scripts": {
    "start:dev": "nest start --watch",
    "build": "nest build",
    "lint": "eslint \"src/**/*.ts\"",
    "typecheck": "tsc --noEmit",
    "format": "prettier --write \"src/**/*.ts\""
  }
}

ESLint 管代码规范、Prettier 管格式、tsc --noEmit 管类型，三者互不替代。CI 里按 lint → typecheck → build 顺序跑，越靠前越便宜，失败更早暴露。

Docker Compose 起 MySQL + Redis

读完你要能做到：一条命令起全套，删容器重建后数据仍在，并且 3306 / 6379 没有暴露到公网。

5.1 四个概念

概念要点
services一个服务 = 一类容器及其配置；compose 会为所有服务建一张默认网络，服务名即可当主机名互访
volumes命名卷由 Docker 管理，独立于容器生命周期。数据在卷里，容器销毁不丢数据；危险操作是 down -v 和 volume prune
healthcheck让 Docker 判断服务是否真正就绪；depends_on 只保证启动顺序，不保证就绪，要配 condition: service_healthy
ports写 127.0.0.1:3306:3306 只对本机开放；直接写 3306:3306 会绑到所有网卡，服务器上等于把数据库暴露公网

GitHub Actions CI 骨架

读完你要能做到：push 后自动跑 lint / typecheck / build，本地与 CI 各跑一次并都修绿。

GitHub Actions 是 CI/CD 平台：在仓库里放一个 workflow（YAML），由事件触发，包含一个或多个 job，job 里按顺序执行 step。W1 只需要六个词：on（触发事件）、jobs、runs-on（运行器）、steps、uses（复用现成 action）、run（执行命令）。

.github/workflows/ci.ymlname: ci

on:
  push:
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: corepack enable
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm typecheck
      - run: pnpm build

corepack enable 必须写在 setup-node 之前，否则 cache: pnpm 找不到 pnpm 会报错；--frozen-lockfile 保证 CI 与本地依赖完全一致。W8 会在这条链里插入 test 与 migration 门禁，W11 再加 deploy。

常见坑：YAML 缩进用空格不用 Tab；node-version 加引号避免被解析成数字；把 .env 当 CI 变量用——密钥要走仓库 Secrets；本地能跑但 CI 红，多数是 lockfile 未提交或 Node 版本不一致。
自测
  1. uses 和 run 的区别？→ uses 复用现成 action，run 在运行器上执行 shell 命令。
  2. 为什么本期 CI 不加 test？→ W4 才引入集成测试，W8 才把它变成合并门禁；W1 先把 lint/typecheck/build 跑通即可。
